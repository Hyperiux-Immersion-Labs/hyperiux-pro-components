# zoom-slider (carousels)

## Summary

`zoom-slider` is a free-tier, GSAP-powered infinite horizontal carousel that maps scroll/drag/touch input through a quadratic easing curve to grow the "active" card as it approaches center screen, with SplitText line-reveal captions on hover. The core animation math and DOM-mutation-over-React-state approach are solid and the registry.json schema itself is correctly formed, but the audit found three classes of real problems: (1) the shipped-to-CLI public mirror has drifted out of sync with the canonical registry source (missing an accessibility feature that was already added upstream), (2) the live marketing demo renders a hand-modified duplicate component with materially different drag physics and DOM structure than what a customer actually receives via install, and (3) the interaction model (hover-only caption reveal, wheel/drag/touch-only slide advance) has no keyboard equivalent, which blocks keyboard-only users from the component's core functionality entirely.

## Implementation overview

- [`index.jsx`](registry/effects/carousels/zoom-slider/index.jsx) is a thin wrapper exporting default `ZoomSlider`, hardcoding `title`, `subheading`, and a 10-item `DEFAULT_SLIDER_DATA` array of external image URLs, then rendering [`ZoomSliderComp`](registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx).
- `ZoomSliderComp` keeps a mutable `stateRef` (`current`/`target` scroll offset, drag state) and runs a `requestAnimationFrame` loop ([registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L125-L149](registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L125)) that lerps `current` toward `target` and calls `positionCards`, which directly mutates each card's `style.transform`/`width`/`height` (bypassing React re-renders for the per-frame layout work — a reasonable perf choice).
- Card width/height is derived from a quadratic "ease-in" mapping function `mapVtoX` ([registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L82-L86](registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L82)) so the active card visually grows as it crosses the viewport.
- Input is captured via `wheel`, `mousedown/move/up`, and `touchstart/move/end` listeners on `window` ([registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L187-L193](registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L187)), all torn down in the effect's cleanup.
- A second effect ([registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L209-L292](registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L209)) wires GSAP `SplitText` line-mask reveal animations to `mouseenter`/`mouseleave` on each card's image wrapper, with `split.revert()` and listener removal in cleanup.
- An `aria-live="polite"` region announces the active slide's title as the loop updates `activeIndex` ([registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L142-L145](registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L142), [registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L294-L308](registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L294)).

## Strengths

- Direct DOM mutation for per-frame layout (`positionCards`) instead of driving 10 cards' transforms through React state avoids an expensive re-render cycle every animation frame — good perf instinct for a continuous animation loop.
- Full listener/rAF/GSAP cleanup is present: `cancelAnimationFrame(state.raf)` and all seven `window` listeners are removed in the first effect's cleanup ([registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L197-L206](registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L197)); the hover-effect's `SplitText` instances are `split.revert()`-ed and listeners removed in the second effect's cleanup ([registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L284-L291](registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L284)).
- An `aria-live` region announces slide changes in the canonical source — a genuine accessibility feature that most carousel effects in this class of component skip (see Risk #1 for why it doesn't reliably reach end users, though).
- `next/image` usage with `priority={index < 3}` and a `sizes` attribute tuned to the three breakpoints is a correct LCP/responsive-image pattern ([registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L377-L391](registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L377)).
- registry.json's `files` array is complete and accurate: both physical files (`index.jsx`, `ZoomSliderComp.jsx`) are listed with correct targets, and `main`/`exportName`/`exportKind` correctly point at the real default export.

## Risks and issues

1. **[High] Public CLI mirror (`public/r/zoom-slider.json`) is stale relative to the canonical registry source — the accessibility feature it ships is missing.** The canonical source at [registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L52-L53](registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L52) and [#L142-L145](registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L142) tracks `activeIndex`/`announcedIndexRef` and renders the `aria-live` announcement region ([#L306-L308](registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L306)). The embedded content string in [apps/docs/public/r/zoom-slider.json#L26](apps/docs/public/r/zoom-slider.json#L26) — the file the CLI actually installs from — has none of this: no `activeIndex` state, no `announcedIndexRef`, no `aria-live` div. `developer-new-component.md` explicitly documents this exact failure mode as a "Thing That Will Break It": *"Forgetting to re-run `build:registry` after edits — the docs site and CLI both read from `public/r/`, not the source"* ([developer-new-component.md#L274](developer-new-component.md#L274)), and separately warns that editing code without bumping `version` lets "the registry ... silently serve the new code under the old version number" ([developer-new-component.md#L272](developer-new-component.md#L272)) — both registry.json and the public mirror still read `"version": "1.0.0"` despite the drift. Git history confirms the aria-live feature was added in a dedicated commit (`7dda8e89 TASk- 409 ( Added area lebels on crausels )`) that was never followed by a `build:registry` run for this component. **Net effect: real end users who install `zoom-slider` via the CLI today get a version without the slide-change screen-reader announcement, even though the source of truth has it.**

2. **[Medium] The live marketing demo renders a hand-diverged duplicate, not the registry source — "try before you buy" doesn't reflect what ships.** The demo route imports `@/components/zoom-slider` ([apps/docs/src/app/(marketing)/demo/zoom-slider/page.js#L3](apps/docs/src/app/(marketing)/demo/zoom-slider/page.js#L3)), which resolves to [apps/docs/src/components/zoom-slider/ZoomSliderComp.jsx](apps/docs/src/components/zoom-slider/ZoomSliderComp.jsx) — a separate file from the registry source, not a copy of it. A diff shows it has diverged substantially: momentum/inertia drag physics (`DRAG_LERP_FACTOR`, `MOMENTUM_FRICTION`, velocity tracking, `touchcancel` handling — [apps/docs/src/components/zoom-slider/ZoomSliderComp.jsx#L12-L14](apps/docs/src/components/zoom-slider/ZoomSliderComp.jsx#L12), [#L130-L164](apps/docs/src/components/zoom-slider/ZoomSliderComp.jsx#L130)), `touchAction: 'none'` on the root ([#L330](apps/docs/src/components/zoom-slider/ZoomSliderComp.jsx#L330)), an `h1` instead of `h2` for the title, and different spacing (`top-20`/`max-md:top-25` vs `top-10`). None of this exists in [registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx](registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx). A prospective customer trying the demo experiences smoother momentum-glide dragging and conflict-free touch scrolling that they will not get from the component they actually install.

3. **[High] No keyboard equivalent for the carousel's core interactions.** Slide advance is driven exclusively by `wheel`/`mousedown+mousemove`/`touchstart+touchmove` on `window` ([registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L151-L185](registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L151)); there is no `keydown` handler for arrow keys, `Home`/`End`, or any other keyboard input. The hover-reveal caption animation is bound only to `mouseenter`/`mouseleave` ([registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L281-L282](registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L281)) with no `focus`/`blur` equivalent, and the card elements themselves are plain, non-interactive `<div>`s with no `tabIndex`, `role`, or button semantics ([registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L324-L331](registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L324)). A keyboard-only user cannot advance the carousel or trigger a single caption reveal — the `aria-live` announcement region (Risk #1) narrates a slide change a keyboard user has no way to cause.

4. **[Medium] Continuous `requestAnimationFrame` loop runs unconditionally forever, with no visibility/off-screen suspension.** `tick()` calls `positionCards` and reschedules itself via `requestAnimationFrame` every frame for the full lifetime of the mount, regardless of whether `state.current` has settled at `state.target`, whether the tab is hidden, or whether the component has scrolled off-screen ([registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L125-L149](registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L125)). Per the audit brief, `registry/effects/_shared/README.md` confirms the `createSuspendedRaf`/`createVisibilityGate` pattern was rolled out to `webgl`, `cursor`, three named `backgrounds` packages, and `scroll` categories (F-042 Tasks 1–4) but **not** `carousels`, so this is not a regression against an existing rollout commitment — it is simply an unadopted opportunity. Flagged at Medium per the audit's explicit severity instruction for this category.

5. **[Medium] No `prefers-reduced-motion` handling anywhere in the component.** Neither the continuous position-lerp loop nor the GSAP hover timelines (`SplitText` line reveals, image scale-in) check `window.matchMedia('(prefers-reduced-motion: reduce)')` — confirmed via `grep` for `prefers-reduced-motion`/`matchMedia` across both [registry/effects/carousels/zoom-slider/](registry/effects/carousels/zoom-slider/) and [apps/docs/src/components/zoom-slider/](apps/docs/src/components/zoom-slider/), which returned no matches in either.

6. **[Medium] Registry source lacks `touchAction: 'none'`, unlike the demo's diverged copy — plausible native-scroll/drag conflict on touch devices.** The canonical `ZoomSliderComp` container has no `touchAction` style ([registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L301-L305](registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L301)), and its `touchmove` listener is registered `{ passive: true }` ([registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L192](registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L192)), so it cannot call `preventDefault()` even if it wanted to. On a touch device this means a vertical or horizontal swipe over the slider simultaneously scrolls the page (native touch scroll) and drags the slider's `state.target` — the demo's separately-maintained copy specifically fixes this with `touchAction: 'none'` ([apps/docs/src/components/zoom-slider/ZoomSliderComp.jsx#L330](apps/docs/src/components/zoom-slider/ZoomSliderComp.jsx#L330)), which is itself evidence the conflict is real and was already discovered once. **Not confirmed with an on-device test in this audit** — flagged from code inspection only.

7. **[Medium] Default demo data hardcodes an external image host with no consumer-side `next.config.js` guarantee.** `DEFAULT_SLIDER_DATA` in [registry/effects/carousels/zoom-slider/index.jsx#L17-L78](registry/effects/carousels/zoom-slider/index.jsx#L17) hardcodes ten `next/image` `src` values on `pub-8abee449136941f5b0a1cd2c014534e9.r2.dev`. This repo's own `apps/docs/next.config.mjs` allows it only because it wildcards all HTTPS hosts ([apps/docs/next.config.mjs#L139-L144](apps/docs/next.config.mjs#L139): `hostname: "**"`). A consumer who installs this component via the CLI and renders `<ZoomSlider />` unmodified in a typical Next.js app (without a wildcard `remotePatterns`) will hit Next's "hostname is not configured under images" runtime error on the very first render, unless they either add that host to their own `remotePatterns` or replace `sliderData` entirely — neither of which is called out anywhere in the component or its metadata.

8. **[Medium] `package.json` uses `dependencies` instead of the documented `peerDependencies`, and omits `react`.** `developer-new-component.md` states the effect package.json's three load-bearing fields are `name`, `version`, and `peerDependencies` ("list `react` and any major packages like `gsap`" — [developer-new-component.md#L163-L166](developer-new-component.md#L163)). [registry/effects/carousels/zoom-slider/package.json#L14-L16](registry/effects/carousels/zoom-slider/package.json#L14) instead declares `"dependencies": { "gsap": "*" }` with no `react` entry at all. This only affects the `npm pack` tarball distribution path (Step 9 of the doc), not the primary CLI/registry.json install path, which is why it's scoped to Medium rather than High.

## Accessibility assessment

- Genuine positive: `aria-live="polite"` slide announcement exists in the canonical source (Risk #1 covers why it may not reach real installs).
- Genuine negative and the most serious finding in this audit: zero keyboard affordance for the carousel's core interaction or for the hover-reveal captions (Risk #3). This is a hard blocker for keyboard-only and many screen-reader users, not a nice-to-have gap.
- Images use `item.title` as `alt` text ([registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L379](registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L379)) — short, non-descriptive one-word alt text (e.g. `"AURA"`, `"DRIFT"`) rather than a description of the image content; acceptable as a stylistic choice for an abstract art carousel but worth noting since it provides no actual image description to screen-reader users.
- No `prefers-reduced-motion` handling (Risk #5).
- Text captions are `visibility: hidden` by default and only shown via GSAP `autoAlpha` on hover ([registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L235](registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L235), [#L246](registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L246)) — since there's no keyboard/focus trigger, this content is unreachable by anyone who can't use a mouse, not just visually hidden-then-revealed.

## Performance assessment

- Always-on rAF loop with per-frame style writes to all 10 cards regardless of idle state or visibility (Risk #4); not currently suspended off-screen or on tab-hide.
- Positioning work mutates `style.transform`/`width`/`height` directly rather than going through React state/re-render, which is the correct choice for a 60fps-driven layout — this avoids the alternative (and worse) pattern of re-rendering 10 child components every frame.
- `viewportWidth`/`viewportHeight` start at hardcoded defaults (`1440`/`900` — [registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L30-L31](registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L30)) and are corrected in a `useEffect` on mount ([#L55-L65](registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L55)). On any real viewport that isn't 1440×900, this causes an initial layout computed at the wrong dimensions before the resize effect fires — a plausible (not measured in this audit) source of a one-frame layout shift on load, particularly on mobile where the default (`1440` ≥ `TABLET_BREAKPOINT`) briefly misclassifies the viewport as desktop.
- No automated performance test/benchmark exists in this repo for this component; the above rAF/CLS claims are based on code reading only, not a captured trace — stated explicitly per the audit's evidence standard.

## SEO and content-surface assessment

- `getDemoPageMetadata("zoom-slider")` is wired into the demo route for metadata generation ([apps/docs/src/app/(marketing)/demo/zoom-slider/page.js#L20-L22](apps/docs/src/app/(marketing)/demo/zoom-slider/page.js#L20)) — metadata sourcing itself was not further traced as it is outside this component's own files.
- Canonical registry source uses `h2` for the on-screen title ([registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L311](registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L311)); the demo's diverged copy uses `h1` instead ([apps/docs/src/components/zoom-slider/ZoomSliderComp.jsx#L337](apps/docs/src/components/zoom-slider/ZoomSliderComp.jsx#L337)). `DemoHeader.jsx` was checked and contains no competing `h1`, so this is not currently causing a duplicate-`h1` problem on the live demo page, but it is one more concrete symptom of the source/demo divergence in Risk #2 and worth normalizing.
- All slider text content (`number`, `title`, `desc`) is rendered as plain text nodes from prop data, not `dangerouslySetInnerHTML` — no injection surface found.

## Responsive / mobile / touch behavior assessment

- Three explicit breakpoints (`MOBILE_BREAKPOINT = 640`, `TABLET_BREAKPOINT = 1025`) drive distinct card width/height/step values ([registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L12-L43](registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L12)), recalculated on every `resize` event.
- Touch input is handled via dedicated `touchstart`/`touchmove`/`touchend` listeners mirroring the mouse-drag logic ([registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L171-L185](registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L171)), so touch is a first-class input path, not a mouse-only afterthought.
- Risk #6 (missing `touchAction: 'none'`) is the standout concern here — a plausible native-scroll-vs-drag conflict on touch devices in the canonical/shipped version, not confirmed by device testing in this audit.
- `100svh` is used for the root height ([registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L304](registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L304)), which is the correct modern unit for avoiding mobile browser chrome/viewport-resize jank (better than plain `100vh`).

## Maintainability and code-quality assessment

- File structure roughly follows `CODING_STANDARDS.md`'s prescribed order (constants → component → state/refs → effects → return), though section-comment markers (`// Renderer and scene`, etc.) called for by the standard are absent — a Low/cosmetic gap, not flagged as a standalone finding.
- Naming is clear and consistent (`SCREAMING_SNAKE_CASE` constants, `camelCase` elsewhere, `onEventName` handlers) matching `CODING_STANDARDS.md` §2.
- The three-way divergence between (a) `registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx`, (b) `apps/docs/public/r/zoom-slider.json`'s embedded content, and (c) `apps/docs/src/components/zoom-slider/ZoomSliderComp.jsx` is the dominant maintainability risk for this component — three copies of similar logic with no single source of truth currently in sync (Risks #1 and #2).
- `package.json` schema deviation (Risk #8) is a smaller, contained maintainability gap limited to the `npm pack` distribution path.

## Security and dependency concerns

- No secrets, tokens, or credentials found in any of the four files reviewed.
- No `dangerouslySetInnerHTML`, `eval`, or dynamic script injection — content is all plain-text React children from prop data, no XSS surface identified.
- `gsap` is declared as `"*"` in both `registry.json` (`dependencies`) and `package.json` (`dependencies`) with no minimum version floor. `SplitText` only ships as a free, bundled GSAP plugin starting with GSAP 3.13; a consumer with an older `gsap` already pinned in their project could hit an import/runtime failure on `SplitText.create` ([registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L226](registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L226)). This is inferred from GSAP's known plugin-licensing history, not verified against this repo's own gsap version pin — flagged as a real but unconfirmed risk.
- External image host (`pub-8abee449136941f5b0a1cd2c014534e9.r2.dev`) is a third-party CDN outside the registry's own control; no integrity/CSP concern found beyond the `next.config.js` allowlist gap already covered in Risk #7.

## Browser compatibility considerations

- `requestAnimationFrame`, `IntersectionObserver` (not used here), `matchMedia` (not used here — see Risk #5), and CSS `100svh` are all modern-baseline features; `100svh` specifically requires a reasonably recent browser (broadly supported in current evergreen browsers, but not legacy ones) — no fallback to `100vh` is provided, which is a minor, unflagged compatibility note rather than a standalone finding given this registry's stated modern-browser target.
- `touch-action` CSS (relevant to Risk #6) has broad modern support; its absence in the canonical source is a behavioral gap, not a compatibility gap.
- No vendor-prefixed CSS or IE-era APIs in use.

## What was checked and found clean

- `registry.json` schema conformance: `name` matches the folder (`zoom-slider`), `type` is exactly `"registry:component"`, `category` is exactly `"carousels"`, `main` (`index.jsx`) exists on disk, `previewUrl` (`/demo/zoom-slider`) matches the real demo route, and every file referenced in `files` (`index.jsx`, `ZoomSliderComp.jsx`) exists with a correct `target` path — no schema violations found in `registry.json` itself.
- No `@/`-style imports between the component's own files — `index.jsx` imports `ZoomSliderComp` via a relative path (`./ZoomSliderComp`), per `developer-new-component.md`'s explicit warning against `@/` imports between own files.
- No stale/duplicate source files sitting in the registry folder that could confuse `build-registry.js`'s extension-based entry-point detection — `ls` of the folder shows exactly the four expected files (`ZoomSliderComp.jsx`, `index.jsx`, `package.json`, `registry.json`).
- Event listener and `requestAnimationFrame` cleanup on unmount is present and complete for the drag/wheel/touch effect (`useEffect` return at [registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L197-L206](registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L197)) and for the hover/`SplitText` effect (return at [#L291](registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx#L291)) — no leaked listeners or dangling `SplitText` instances identified.
- No WebGL context/resources in this component (not a `webgl`-category effect), so no disposal checklist applies.
- No secrets or credentials in source (see Security section).

## Suggested improvements and remediation priorities

No code was changed as part of this audit, per `CHANGE_GUIDELINES.md`. Suggested priority order for a follow-up fix pass (any actual fix must be verified not to break the CLI install flow, the demo page, or existing responsive/touch behavior before landing):

1. Re-run `build:registry` for `zoom-slider` (and audit whether other components have the same drift) and bump `version` per the documented workflow, so `public/r/zoom-slider.json` matches the canonical source (addresses Risk #1).
2. Reconcile `apps/docs/src/components/zoom-slider/ZoomSliderComp.jsx` with the registry source — either promote the momentum-drag/`touchAction` improvements back into `registry/effects/carousels/zoom-slider/ZoomSliderComp.jsx` (if they're an intended upgrade) or replace the demo's hand copy with a direct import of the registry source, so the demo truthfully represents the installed product (Risk #2).
3. Add a keyboard interaction path — at minimum, `ArrowLeft`/`ArrowRight` to step `state.target` by one `cardStep`, and `focus`/`blur` handlers mirroring `mouseenter`/`mouseleave` on each card — before the hover-caption feature can be considered accessible (Risk #3).
4. Adopt a local copy of `createSuspendedRaf`/`createVisibilityGate` per `registry/effects/_shared/README.md`'s pattern to pause the rAF loop off-screen/tab-hidden (Risk #4).
5. Gate the hover/GSAP timelines and the continuous position-lerp behind a `prefers-reduced-motion` check (Risk #5).
6. Add `touchAction: 'none'` (or scoped equivalent) to the canonical source's root container, matching the fix already present in the demo's diverged copy (Risk #6) — verify on an actual touch device before landing, since this audit did not confirm the conflict at runtime.
7. Either document the `next.config.js` `remotePatterns` requirement for the default demo data's image host, or swap `DEFAULT_SLIDER_DATA` to same-origin/documented placeholder assets (Risk #7).
8. Correct `package.json` to use `peerDependencies` (including `react`) per `developer-new-component.md` (Risk #8).

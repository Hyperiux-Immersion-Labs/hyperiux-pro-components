# scramble-link-button (buttons)

## Summary

`scramble-link-button` is a single-file (`index.jsx`), free-tier Next.js link component that scrambles its label text through random glyphs on hover/press before settling on the real label, with optional underline and rotating arrow icon. The `registry.json` is schema-complete and internally consistent, and the public mirror (`apps/docs/public/r/scramble-link-button.json`) is byte-identical to the registry source, so the primary JSON-based CLI install path works correctly. However, two concrete functional defects were found: the component's NPM tarball (`registry/dist/hyperiux-scramble-link-button-0.0.1.tgz`) is missing the actual component source because `package.json` points at a file that doesn't exist (and lacks `peerDependencies` entirely), and the touch/mobile "pressed" visual state is set but never cleared, leaving the hover styling stuck on after any tap on narrow viewports. The docs demo also renders a stale, diverged legacy copy of the component (different prop name) rather than the registry source, so what a prospective user sees in the live demo is not proof of what the registry component actually does. Smaller gaps round out the picture: an inconsistent `onMouseEnter` prop-forwarding path (unlike the pointer handlers, which forward correctly), no accessible name when `btnText` is omitted, and no `prefers-reduced-motion` handling.

## Implementation overview

- `registry/effects/buttons/scramble-link-button/index.jsx` exports `ScrambleLinkButton` (named + default), wrapping Next.js `Link`.
- `getScrambledText()` ([index.jsx#L16-L44](../../../registry/effects/buttons/scramble-link-button/index.jsx#L16-L44)) computes, per character index, a per-glyph reveal threshold based on `iteration`, `maxIterations`, and `revealStagger`, so characters resolve left-to-right in a staggered wave rather than all at once.
- `runScramble()` ([index.jsx#L114-L146](../../../registry/effects/buttons/scramble-link-button/index.jsx#L114-L146)) drives the animation via a chained `setTimeout` loop (not `requestAnimationFrame`), stepping every `stepMs` (default 50ms) for `scrambleDuration / stepMs` iterations (default 20), then forces the final text.
- Two stacked `<span>`s create a layout-stable text swap: an `invisible` ghost span reserves width using the real text, and an absolutely-positioned sibling span (`scrambleRef`) is mutated via `textContent` during the scramble and carries `aria-label={btnText}` ([index.jsx#L185-L200](../../../registry/effects/buttons/scramble-link-button/index.jsx#L185-L200)).
- A `matchMedia` listener ([index.jsx#L92-L112](../../../registry/effects/buttons/scramble-link-button/index.jsx#L92-L112)) tracks whether the viewport is below `COMPACT_LAYOUT_BREAKPOINT - 1` (1024px, i.e. Tailwind's `lg` boundary) and toggles `isCompactLayout`, which gates a pointer-based "pressed" affordance for touch (`handlePointerDown` at [index.jsx#L152-L161](../../../registry/effects/buttons/scramble-link-button/index.jsx#L152-L161)) since `:hover` doesn't exist on touch devices.

## Strengths

- Accessible-name stability under animation: instead of letting screen readers read out scrambling glyphs, the visible span carries a static `aria-label={btnText}` ([index.jsx#L197](../../../registry/effects/buttons/scramble-link-button/index.jsx#L197)) so assistive tech announces the real label regardless of the in-progress scramble — a deliberate, correct choice.
- Layout-stable text swap: the invisible ghost span reserves box dimensions ahead of the absolutely-positioned scrambled span, avoiding layout shift as scrambled glyphs (which may render at different widths than the final text) are swapped in.
- Bounded, self-terminating animation: `runScramble` always converges to `maxIterations` and force-sets the exact final text ([index.jsx#L136-L139](../../../registry/effects/buttons/scramble-link-button/index.jsx#L136-L139)), so there's no risk of characters getting stuck mid-scramble.
- Correct prop-composition order for pass-through handlers: `onPointerDown`/`onPointerUp`/`onPointerCancel` are left inside `...props` and explicitly re-invoked (`props.onPointerDown?.(event)`) inside the component's own handlers before those handlers are placed after `{...props}` in JSX ([index.jsx#L152-L169](../../../registry/effects/buttons/scramble-link-button/index.jsx#L152-L169)), so a consumer's own pointer handlers still fire.
- `registry.json` is fully schema-compliant (see Risks section — no defects found there).

## Risks and issues

1. **[High] NPM tarball distribution is broken — the packed component contains no source code.** `registry/effects/buttons/scramble-link-button/package.json#L5-L9` declares `"main": "scramble-link-button.jsx"` and `"files": ["scramble-link-button.jsx", "registry.json"]`, but no file named `scramble-link-button.jsx` exists anywhere in the folder — the actual source is `index.jsx`. This was verified directly against the built artifact: `tar -tzf registry/dist/hyperiux-scramble-link-button-0.0.1.tgz` lists only `package/package.json` and `package/registry.json` — `index.jsx` is absent from the tarball entirely. Anyone installing this component via the npm tarball gets a package with no component code. Note: the primary CLI install path (`apps/docs/public/r/scramble-link-button.json`, which embeds the full free-tier source per `developer-new-component.md` Step 6) is unaffected and correct, which is why this is scoped High rather than Critical — but the packaged-npm distribution channel described in `developer-new-component.md` Step 9 is confirmed non-functional for this component.

2. **[High] Touch/mobile "pressed" state is set but never cleared — hover styling gets stuck on after a tap.** `handlePointerDown` ([index.jsx#L152-L161](../../../registry/effects/buttons/scramble-link-button/index.jsx#L152-L161)) calls `setIsPressed(true)` for any non-mouse pointer while `isCompactLayout` is true (viewport < 1025px). Neither `handlePointerUp` nor `handlePointerCancel` ([index.jsx#L163-L169](../../../registry/effects/buttons/scramble-link-button/index.jsx#L163-L169)) ever calls `setIsPressed(false)`. The only place `isPressed` is reset is inside the `matchMedia` change handler when the viewport crosses back above the breakpoint ([index.jsx#L101-L103](../../../registry/effects/buttons/scramble-link-button/index.jsx#L101-L103)), which will not happen on an actual mobile device. Concretely: tap the link once on any viewport under 1025px (e.g. a real phone), and `data-pressed="true"` persists, so `group-data-[pressed=true]:text-(--scramble-hover-color)` and the underline-in styles ([index.jsx#L182](../../../registry/effects/buttons/scramble-link-button/index.jsx#L182), [index.jsx#L76](../../../registry/effects/buttons/scramble-link-button/index.jsx#L76)) stay permanently applied — the link is stuck in its "hovered/active" color for the rest of the page's life. This reproduces whenever the tap doesn't unmount the component (e.g. `href="#"`, a same-page anchor, or `target="_blank"`).

3. **[Medium] The live demo renders a stale, diverged duplicate of the component, not the registry source.** `apps/docs/src/app/(marketing)/demo/scramble-link-button/page.js#L1` imports `ScrambleLinkButton` from `@/components/scramble-link-button`, which resolves to `apps/docs/src/components/scramble-link-button/index.jsx` — a legacy copy, not `registry/effects/buttons/scramble-link-button/index.jsx`. The two have diverged: the legacy copy accepts a `text` prop (plus a `children`-as-text fallback) and adds a `scale-150` class ([apps/docs/src/components/scramble-link-button/index.jsx#L46-L71](../../../apps/docs/src/components/scramble-link-button/index.jsx#L46-L71), [#L186](../../../apps/docs/src/components/scramble-link-button/index.jsx#L186)), while the registry component only accepts `btnText` and has no `children` support ([registry/effects/buttons/scramble-link-button/index.jsx#L46-L58](../../../registry/effects/buttons/scramble-link-button/index.jsx#L46-L58)). The demo page passes `text="Hover me"` ([apps/docs/src/app/(marketing)/demo/scramble-link-button/page.js#L25](../../../apps/docs/src/app/(marketing)/demo/scramble-link-button/page.js#L25)); if the demo were switched to import the actual registry component with that same prop, the button would silently render with empty text (since `btnText` would be undefined and default to `""`). `developer-new-component.md`'s "Things That Will Break It" section warns specifically about stale duplicate source files causing silent divergence — this is that same failure class, one level up (docs-app copy vs. registry source rather than two files inside the registry folder itself). Net effect: the demo a prospective user evaluates does not prove anything about the shipped registry component's actual prop API or behavior.

4. **[Medium] No accessible name if `btnText` is omitted (e.g. icon-only usage).** `DEFAULT_BTN_TEXT = ""` ([index.jsx#L7](../../../registry/effects/buttons/scramble-link-button/index.jsx#L7)), and the only accessible-name source for the link is `aria-label={btnText}` on the visible span ([index.jsx#L197](../../../registry/effects/buttons/scramble-link-button/index.jsx#L197)) — the ghost span is excluded from accessible-name computation because it's `invisible` (`visibility: hidden`), and the optional arrow icon ([index.jsx#L203-L209](../../../registry/effects/buttons/scramble-link-button/index.jsx#L203-L209)) has no `aria-label`/`title`/`aria-hidden`. A consumer rendering `<ScrambleLinkButton href="/x" showArrow />` without `btnText` — a plausible icon-forward CTA usage given `showArrow`/`icon` are first-class props — produces an `<a>` with an empty `aria-label` and no fallback text, i.e. an unlabeled link, which is undiscoverable by screen-reader and voice-control users navigating by link name. There is no runtime guard or dev-time warning for this.

5. **[Medium] No `prefers-reduced-motion` handling.** Nothing in `index.jsx` checks `window.matchMedia('(prefers-reduced-motion: reduce)')` (confirmed via `grep -rn "reduced-motion" registry/effects/buttons/` returning no matches for this component). The scramble replaces the visible label with random glyphs on every hover/tap-press regardless of the user's OS-level motion preference. This is not a continuous `requestAnimationFrame` loop (it's a bounded, ~1s `setTimeout` chain that only runs on interaction), so the rubric's rAF-suspension case doesn't strictly apply, but the missing-best-practice impact (motion-sensitive users can't opt this specific effect out) is real and bounded, matching the rubric's Medium example directly.

6. **[Low] No keyboard/focus parity for the scramble trigger.** `runScramble()` is wired to `onMouseEnter` ([index.jsx#L148-L150](../../../registry/effects/buttons/scramble-link-button/index.jsx#L148-L150)) and to `pointerdown` only in compact layout ([index.jsx#L152-L161](../../../registry/effects/buttons/scramble-link-button/index.jsx#L152-L161)); there is no `onFocus` handler. A keyboard user tabbing to the link never triggers the scramble animation — the link remains fully operable (native `<a>`, default focus ring, Enter activates it), so this is a cosmetic-parity gap rather than a functional block.

7. **[Low] Minor style nits.** A double space in the `className` template literal (`"...gap-2  text-[1.1vw]..."`, [index.jsx#L182](../../../registry/effects/buttons/scramble-link-button/index.jsx#L182)); the "Derived values" block (`activeTextStyle`/`activeLineStyle`/`innerClassName`, [index.jsx#L69-L78](../../../registry/effects/buttons/scramble-link-button/index.jsx#L69-L78)) is placed before the Effects block rather than after, diverging from the file-structure order in `CODING_STANDARDS.md` §1 (State & Refs → Effects → Derived values → Return).

8. **[Medium] `onMouseEnter` silently drops a consumer-supplied handler, unlike the pointer handlers.** The explicit `onPointerDown`/`onPointerUp`/`onPointerCancel` handlers each re-invoke `props.onPointerDown?.(event)` etc. before doing their own work ([index.jsx#L152-L169](../../../registry/effects/buttons/scramble-link-button/index.jsx#L152-L169)), so a consumer's own pointer handler still fires even though it's shadowed in the JSX. `onMouseEnter` does not follow this pattern: the internal `onMouseEnter` handler ([index.jsx#L148-L150](../../../registry/effects/buttons/scramble-link-button/index.jsx#L148-L150)) never calls `props.onMouseEnter?.(event)`, and because `onMouseEnter={onMouseEnter}` is placed after `{...props}` in the JSX ([index.jsx#L177](../../../registry/effects/buttons/scramble-link-button/index.jsx#L177)), any `onMouseEnter` a consumer passes through `...props` is silently overwritten and never called. This is an inconsistency with the pattern used two lines below in the same component, not just a missing feature.

9. **[Medium] `package.json` has no `peerDependencies`.** `developer-new-component.md` Step 5 requires package.json to list `peerDependencies` for `react` and any major packages the component depends on. [registry/effects/buttons/scramble-link-button/package.json](../../../registry/effects/buttons/scramble-link-button/package.json) has no `peerDependencies` field at all, despite the component hard-depending on `react` and `next/link`. This is on top of finding 1 (the wrong `main`/`files` entry) — the package.json is incomplete in two independent ways relative to the documented schema. Impact is bounded to the already-broken npm-tarball channel, not the primary CLI/JSON install path.

## Accessibility assessment

- Positive: the `aria-label` pinned to the final text keeps the announced name stable while the visible text scrambles (Strengths, above), and the underlying element is a real `<a>` via Next `Link`, so it's natively focusable and keyboard-operable (Tab + Enter) without any extra work.
- Gap (Medium, finding 4): if `btnText` is omitted, the link has no accessible name at all.
- Gap (Low, finding 6): no focus-triggered scramble, so keyboard users don't get the same visual affordance as mouse/touch users (non-blocking).
- Not checked: actual color contrast of `hoverColor` (`#ff6b00` default) against arbitrary consumer backgrounds — this is consumer-supplied and out of the component's control, so not scoreable here.

## Performance assessment

- Animation is driven by a chained `setTimeout` (not `requestAnimationFrame`), bounded to `Math.max(1, Math.floor(scrambleDuration / stepMs))` iterations (20 by default) and only runs while the pointer is hovering/pressing — it is not a continuous loop, so the rAF-suspension pattern (`createSuspendedRaf`/`createVisibilityGate` from `registry/effects/_shared/README.md`) does not apply here per the audit's own guidance (only flagged when a genuine continuous rAF loop exists).
- Cleanup on unmount is present: the text-sync effect's cleanup clears `timeoutRef.current` ([index.jsx#L85-L89](../../../registry/effects/buttons/scramble-link-button/index.jsx#L85-L89)), and the `matchMedia` listener is removed on unmount ([index.jsx#L109-L111](../../../registry/effects/buttons/scramble-link-button/index.jsx#L109-L111)). No dangling timers or listeners were found.
- `runScramble` clears any in-flight timeout before starting a new one ([index.jsx#L121-L123](../../../registry/effects/buttons/scramble-link-button/index.jsx#L121-L123)), so rapid re-hovers cannot stack overlapping scramble loops.
- No automated performance test/benchmark exists in this repo for this component; the above is a static-code assessment, not a measured one.

## SEO and content-surface assessment

- The button's real text is present in the DOM at all times (both the ghost span and the scramble span render `{btnText}` server-side; only `textContent` is mutated client-side during the hover animation), so crawlers and any pre-hydration snapshot see the actual label — no SEO-relevant content is hidden behind JS-only rendering.
- Uses Next.js `Link`, which is crawlable/prefetchable, consistent with the rest of the `buttons` category (`char-stagger-primary-button`, `arrow-fill-button`, `char-stagger-button`, `link-button` all use `next/link` too — this is a category-wide convention, not unique to this component).

## Responsive / mobile / touch behavior assessment

- Font sizing uses viewport units with breakpoint overrides (`text-[1.1vw]`, `max-lg:text-[3vw]`, `max-sm:text-[4.2vw]`, [index.jsx#L182](../../../registry/effects/buttons/scramble-link-button/index.jsx#L182)), consistent with the `COMPACT_LAYOUT_BREAKPOINT = 1025` constant, which is deliberately aligned to Tailwind's `lg` breakpoint (1024px) minus 1.
- The touch-specific "pressed" affordance is a good idea in principle (touch has no `:hover`), but its implementation has the state-reset bug documented as finding 2 (High) above — this is the most consequential mobile-specific defect found.

## Maintainability and code-quality assessment

- Constants are correctly hoisted to module scope and named in `SCREAMING_SNAKE_CASE` per `CODING_STANDARDS.md` §2 (`DEFAULT_BTN_TEXT`, `COMPACT_LAYOUT_BREAKPOINT`, `GLYPHS`, etc., [index.jsx#L7-L14](../../../registry/effects/buttons/scramble-link-button/index.jsx#L7-L14)).
- `getScrambledText` is a small, pure, testable helper extracted from the component body — good separation.
- Event handler names follow the `onEventName`/`handleEventName` convention from `CODING_STANDARDS.md` §2.
- Minor structural/style deviations noted in finding 7 (Low).

## Security and dependency concerns

- No use of `dangerouslySetInnerHTML`, `eval`, or unescaped HTML injection; text is written via `textContent`, which is XSS-safe by construction.
- No secrets, tokens, or credentials present in source.
- `href` is passed straight through to Next `Link` without sanitization, but this is standard for a link component and Next `Link` does not execute `href` as code — not a finding.
- Declared dependency (`lucide-react`) in `registry.json` matches the only external import (`ArrowRight`); `next` (for `next/link`) is used but not declared as a dependency — this matches the convention of every other `next/link`-using component in the `buttons` category (`dot-fill-button`, `link-button`, `arrow-fill-button`, `char-stagger-button`, `char-stagger-primary-button` all follow the same pattern), so it is treated as an accepted category-wide convention rather than a component-specific defect.

## Browser compatibility considerations

- `window.matchMedia` and `MediaQueryList.addEventListener` are used ([index.jsx#L93-L112](../../../registry/effects/buttons/scramble-link-button/index.jsx#L93-L112)); both are broadly supported in evergreen browsers (Safari 14+, Chrome/Firefox/Edge current). No legacy `addListener`/`removeListener` fallback is present, which is an accepted trade-off given this is a modern-browser-targeted component library.
- No use of bleeding-edge CSS beyond Tailwind v4 arbitrary-value/CSS-variable syntax (`text-(--scramble-hover-color)`), which is a build-tool (Tailwind v4) dependency, not a runtime browser-compat risk — Tailwind compiles this to standard CSS custom properties.
- Optional chaining (`?.`) is used ([index.jsx#L153](../../../registry/effects/buttons/scramble-link-button/index.jsx#L153), [#L164](../../../registry/effects/buttons/scramble-link-button/index.jsx#L164), [#L168](../../../registry/effects/buttons/scramble-link-button/index.jsx#L168)), which requires modern JS support but is universal in evergreen browsers and is transpiled by the Next.js build if older targets are configured.

## What was checked and found clean

- `registry.json` schema completeness against `developer-new-component.md`: `name` matches folder exactly, `type` is `"registry:component"`, `category` is exactly `"buttons"` (valid enum value), `main` (`index.jsx`) exists, `exportName`/`exportKind` match the actual export, `previewUrl` (`/demo/scramble-link-button`) matches the demo route folder, `target`/`files[].target` are internally consistent, and the single `files` entry correctly covers the component's only source file (no missing sub-files, since there are no sub-files to miss).
- Public mirror (`apps/docs/public/r/scramble-link-button.json`) embedded `content` was diffed by inspection against `registry/effects/buttons/scramble-link-button/index.jsx` and found byte-identical — no drift between registry source and the public JSON the CLI actually serves for this free-tier component.
- The `target` path difference between `registry.json` (`src/components/effects/scramble-link-button/index.jsx`) and the public mirror (`components/hyperiux/index.jsx`) was spot-checked against a sibling component (`dot-fill-button`) and found to be an identical, systemic build-script transformation applied to every effect — not a defect specific to this component.
- Root registry index (`registry/index.json#L144-L153`) has a correct, complete entry for `scramble-link-button` matching the component's registry.json fields.
- No slug alias entry exists in `apps/docs/src/lib/effect-slugs.js` for this component, and none appears necessary (no evidence of a prior rename or alternate name).
- rAF-suspension pattern (`createSuspendedRaf`/`createVisibilityGate`): correctly not present, and correctly not required — this component has no continuous `requestAnimationFrame` loop (confirmed: only `setTimeout` is used, bounded to a fixed iteration count per interaction).
- Cleanup on unmount for the timeout and the media-query listener is present and correct (see Performance assessment).
- No use of `dangerouslySetInnerHTML`, `eval`, or hardcoded secrets (see Security assessment).

## Suggested improvements and remediation priorities

No code was changed as part of this audit. If addressed later, per `CHANGE_GUIDELINES.md` any fix must not alter the visual/UI behavior of correctly-used instances or break registry install behavior. Suggested priority order:

1. Fix `package.json`'s `main`/`files` to reference `index.jsx` instead of the nonexistent `scramble-link-button.jsx`, then re-run `npm pack` and replace `registry/dist/hyperiux-scramble-link-button-0.0.1.tgz` (finding 1, High). Worth checking whether this same `{slug}.jsx`-vs-`index.jsx` mismatch exists across other `buttons` packages before fixing just this one, since the pattern was observed in multiple sibling `package.json` files during this audit — but that determination is out of scope for this single-component report.
2. Add `setIsPressed(false)` in `handlePointerUp` and `handlePointerCancel` (finding 2, High) so the pressed/hover state clears correctly on touch devices.
3. Point the demo page at the registry source (or delete/reconcile the legacy `apps/docs/src/components/scramble-link-button/index.jsx` copy) so the demo proves the actual shipped prop API (finding 3, Medium).
4. Consider a fallback accessible name (e.g. warn in dev, or fall back to `href` text) when `btnText` is empty and no `aria-label` override is supplied (finding 4, Medium).
5. Add a `prefers-reduced-motion` check to skip/shorten the scramble animation for users who've opted out at the OS level (finding 5, Medium).
6. Optionally wire `onFocus` to `runScramble` for keyboard-focus parity (finding 6, Low).
7. Cosmetic: fix the double space in the `className` string and reorder the derived-values block after the effects block per `CODING_STANDARDS.md` §1 (finding 7, Low).
8. Forward any consumer-supplied `onMouseEnter` the same way the pointer handlers already forward theirs (finding 8, Medium).
9. Add `peerDependencies` (`react`, `next`) to `package.json` alongside the `main`/`files` fix from finding 1 (finding 9, Medium).

# animated-modal (components)

## Summary

`animated-modal` is a three-file fullscreen dialog (`index.jsx`, `AnimatedModalContent.jsx`, `ScrollablePopupContent.jsx`) that opens a backdrop-blurred, focus-trapped popup with escape/backdrop/close-button dismissal. The core implementation is solid — real focus trapping, focus restoration, `inert`/`aria-hidden` on the closed state, scroll lock, and named cleanup — which puts it ahead of most modal implementations in this category. The issues found are all outside the component logic itself: the registry copy's responsive breakpoints have drifted from the live docs demo copy, the default dialog accessible name is generic, there's no `prefers-reduced-motion` handling, and the packed npm tarball in `registry/dist/` is a stale, pre-refactor single-file version that does not match current source. None of these break the primary CLI/registry install path.

## Implementation overview

- [`registry/effects/components/animated-modal/index.jsx`](../../../registry/effects/components/animated-modal/index.jsx) — default-exported `AnimatedModal`, holds `isContentOpen` state, renders the trigger button and wires `AnimatedModalContent` + `ScrollablePopupContent` with static demo copy (`popupSections`).
- [`registry/effects/components/animated-modal/AnimatedModalContent.jsx`](../../../registry/effects/components/animated-modal/AnimatedModalContent.jsx) — the actual dialog primitive: focus trap, Escape handling, backdrop click-to-close, body scroll lock, `inert`/`aria-hidden` when closed, and a close button.
- [`registry/effects/components/animated-modal/ScrollablePopupContent.jsx`](../../../registry/effects/components/animated-modal/ScrollablePopupContent.jsx) — presentational scrollable content card (title/subtitle/sections) rendered inside the dialog.

## Strengths

- Real focus trap with `Tab`/`Shift+Tab` cycling and a fallback that refocuses the container when there are no focusable descendants ([AnimatedModalContent.jsx#L41-L68](../../../registry/effects/components/animated-modal/AnimatedModalContent.jsx#L41)).
- Focus restoration to the trigger element on close via `previousFocusRef` ([AnimatedModalContent.jsx#L21](../../../registry/effects/components/animated-modal/AnimatedModalContent.jsx#L21), [AnimatedModalContent.jsx#L74-L79](../../../registry/effects/components/animated-modal/AnimatedModalContent.jsx#L74)).
- Uses `inert` + `aria-hidden` on the closed dialog rather than fully unmounting, which keeps assistive tech and tab order correctly excluded without a layout-shift/remount cost when reopened ([AnimatedModalContent.jsx#L91](../../../registry/effects/components/animated-modal/AnimatedModalContent.jsx#L91)).
- Body scroll lock is applied and correctly restored to the *previous* value (not hardcoded to `""`) on cleanup ([AnimatedModalContent.jsx#L71-L76](../../../registry/effects/components/animated-modal/AnimatedModalContent.jsx#L71)).
- Named `handleKeyDown` handler, added and removed with the same reference ([AnimatedModalContent.jsx#L41](../../../registry/effects/components/animated-modal/AnimatedModalContent.jsx#L41), [AnimatedModalContent.jsx#L70](../../../registry/effects/components/animated-modal/AnimatedModalContent.jsx#L70), [AnimatedModalContent.jsx#L75](../../../registry/effects/components/animated-modal/AnimatedModalContent.jsx#L75)) — matches CODING_STANDARDS.md's "name all inline functions" rule.
- `data-lenis-prevent` on the dialog root correctly stops the site's Lenis smooth-scroll library from hijacking scroll inside the modal ([AnimatedModalContent.jsx#L90](../../../registry/effects/components/animated-modal/AnimatedModalContent.jsx#L90)).
- Close button meets the 40×40px (`min-w-10 min-h-10`) minimum touch target ([AnimatedModalContent.jsx#L135](../../../registry/effects/components/animated-modal/AnimatedModalContent.jsx#L135)).
- No continuous `requestAnimationFrame` loop anywhere in the three files (verified via grep) — the open/close motion is a pure CSS `duration-500` opacity transition, so the rAF-suspension pattern from `_shared/README.md` genuinely does not apply here.

## Risks and issues

1. **Medium — Registry copy's responsive breakpoints have drifted from what the demo actually shows.** The registry source (what CLI installs ship) uses a three-tier `max-[1025px]:` / `max-lg:` / `max-md:` breakpoint scheme, while the docs-site demo copy at `apps/docs/src/components/animated-modal/` (what `page.js` actually renders and what a prospective buyer previews) uses the two-tier `max-md:` / `max-sm:` scheme. Confirmed via diff — e.g. trigger button: [registry index.jsx#L64-L65](../../../registry/effects/components/animated-modal/index.jsx#L64) (`max-lg:… max-md:…`) vs [docs index.jsx#L64-L65](../../../apps/docs/src/components/animated-modal/index.jsx#L64) (`max-md:… max-sm:…`); same pattern repeats throughout [registry ScrollablePopupContent.jsx](../../../registry/effects/components/animated-modal/ScrollablePopupContent.jsx#L13) vs [docs ScrollablePopupContent.jsx](../../../apps/docs/src/components/animated-modal/ScrollablePopupContent.jsx#L13). This means the sizing/spacing a buyer previews at `/demo/animated-modal` does not match what they get after `npx hyperiux add animated-modal` at intermediate viewport widths (e.g. the "tablet" breakpoint fires at a different width). It's also a direct deviation from CODING_STANDARDS.md's "Responsive prefixes" rule ("Use `max-sm:` for mobile… `max-md:` for tablet… prefer those breakpoint prefixes consistently instead of mixing multiple mobile/tablet targeting patterns" — [CODING_STANDARDS.md#L274-L278](../../../CODING_STANDARDS.md#L274)), which the docs copy follows and the registry copy does not.
2. **Medium — Generic default accessible name on the dialog.** `index.jsx` renders `<AnimatedModalContent>` without passing `ariaLabel` or `ariaLabelledby` ([index.jsx#L71-L75](../../../registry/effects/components/animated-modal/index.jsx#L71)), so the component falls back to its default `ariaLabel = "Dialog"` ([AnimatedModalContent.jsx#L17](../../../registry/effects/components/animated-modal/AnimatedModalContent.jsx#L17)). A screen-reader user hears only "Dialog" on open, with no indication it's about "A Deeper Look at the Project" — the `<h2>` title rendered inside `ScrollablePopupContent.jsx` ([ScrollablePopupContent.jsx#L22-L26](../../../registry/effects/components/animated-modal/ScrollablePopupContent.jsx#L22)) has no `id`, so it can't be wired to `aria-labelledby` even by a consumer who wants to.
3. **Medium — No `prefers-reduced-motion` handling.** The open/close opacity transition is driven by a flat `duration-500` Tailwind class with no reduced-motion variant anywhere in the three files (grep for `prefers-reduced-motion`/`useReducedMotion`/`matchMedia` returned nothing). Per the audit rubric this is a bounded-impact miss, not a blocker — the animation is a simple opacity fade, not vestibular-trigger-grade motion, but it's still a real gap against the standard applied elsewhere in this registry (e.g. `border-beam`).
4. **Medium — The packed npm distribution tarball for this component is stale and does not match current source.** `registry/dist/hyperiux-modal-0.0.1.tgz` (dated Jun 30, older than any of the three current source files) contains only `package.json`, `registry.json`, and a single `Modal.jsx` — an older, pre-refactor implementation with no focus trap, no `previousFocusRef`, no `ariaLabel`/`ariaLabelledby` props, and no `ScrollablePopupContent` split at all (verified by extracting and reading the packed file). This is a direct instance of the failure mode `developer-new-component.md` warns about under "Things That Will Break It": *"Not bumping the version before re-packing — old tarballs get silently overwritten"* ([developer-new-component.md#L273](../../../developer-new-component.md#L273)). Root cause: `package.json`'s `files`/`main` field points at `modal.jsx` ([package.json#L5-L9](../../../registry/effects/components/animated-modal/package.json#L5)), a filename that doesn't exist in the folder (actual entry is `index.jsx`) — this "files pointing at a nonexistent filename" pattern is repo-wide, not unique to this component (confirmed the same mismatch in `card-drift`, `animated-faq`, `gooey-counter`, etc.), so it isn't a component-specific regression, but for `animated-modal` specifically it happens to still resolve (case-insensitively, `Modal.jsx` ~ `modal.jsx`, verified via `tar -tzf`) to genuinely wrong, outdated content rather than an empty tarball. **Scoped down from High**: this only affects the secondary `npm pack` / `registry/dist/*.tgz` distribution path — I could not find any code in `apps/docs/src` referencing `registry/dist` or `.tgz` files, and the primary CLI install path (`public/r/animated-modal.json`, driven by `registry.json`'s `main: "index.jsx"`) is unaffected and verified current (see below). This item appears to already be tracked at the repo level per `Hyperiux_Vault_Confirmed_Findings_Remediation_Plan.md`.
5. **Low — `package.json` `main`/`files` reference a nonexistent file.** [package.json#L5-L9](../../../registry/effects/components/animated-modal/package.json#L5) lists `"main": "modal.jsx"` / `"files": ["modal.jsx", "registry.json"]`, but the folder has no `modal.jsx` (entry is `index.jsx`, plus two more sub-files not listed at all). This is the direct cause of finding #4. Fixing it is out of scope for this audit (no code changes made), but it's called out separately since it's a `package.json`-schema issue independent of tarball staleness.

## Accessibility assessment

- **Dialog semantics**: `role="dialog"`, `aria-modal="true"`, `tabIndex={-1}` with programmatic focus on open — correct baseline pattern ([AnimatedModalContent.jsx#L85-L89](../../../registry/effects/components/animated-modal/AnimatedModalContent.jsx#L85), [#L39](../../../registry/effects/components/animated-modal/AnimatedModalContent.jsx#L39)).
- **Focus trap & restoration**: implemented correctly, including the empty-focusable-list edge case (see Strengths).
- **Closed-state exclusion**: `inert` + `aria-hidden="true"` applied only when closed ([AnimatedModalContent.jsx#L91](../../../registry/effects/components/animated-modal/AnimatedModalContent.jsx#L91)) — correct and modern (see Browser compatibility below for `inert` support caveats).
- **Keyboard dismissal**: `Escape` closes when `closeOnEsc` (default true) ([AnimatedModalContent.jsx#L42-L45](../../../registry/effects/components/animated-modal/AnimatedModalContent.jsx#L42)).
- **Close button labeling**: both the backdrop-click button and the visible close button carry `aria-label="Close modal"` ([AnimatedModalContent.jsx#L105](../../../registry/effects/components/animated-modal/AnimatedModalContent.jsx#L105), [#L122](../../../registry/effects/components/animated-modal/AnimatedModalContent.jsx#L122)) — good, though having two independently-labeled "Close modal" controls (invisible full-screen backdrop button + visible X button) could be mildly confusing when navigating by AT rotor/landmark list; not flagged as a separate finding since both are legitimately actionable and correctly labeled.
- **Gap**: generic default `aria-label="Dialog"` when the consumer (the demo, `index.jsx`) doesn't supply a more specific label — see finding #2.
- **Heading hierarchy**: demo page's `<h1>` → modal's `<h2>` (`ScrollablePopupContent.jsx#L22`) → `<h3>` per section ([ScrollablePopupContent.jsx#L38](../../../registry/effects/components/animated-modal/ScrollablePopupContent.jsx#L38)) is correctly nested — checked and clean.

## Performance assessment

- No `requestAnimationFrame` loop, no WebGL/canvas, no heavy re-renders — a single `useState` boolean drives the whole component, and the dialog's own `useEffect` only re-runs on `isOpen`/`onClose`/`closeOnEsc` changes ([index.jsx#L51](../../../registry/effects/components/animated-modal/index.jsx#L51), [AnimatedModalContent.jsx#L80](../../../registry/effects/components/animated-modal/AnimatedModalContent.jsx#L80)).
- Content stays mounted (via `inert`) rather than unmounting on close, trading a small always-in-DOM cost for avoiding remount/layout-shift on reopen — a reasonable, deliberate trade-off for this component's content size (a handful of text sections). Not flagged as an issue; would only matter if a consumer put something expensive (video, heavy image gallery) inside.
- No cross-effect rAF-suspension pattern needed — confirmed by grep, no continuous animation loop exists.

## SEO and content-surface assessment

- Modal content (project overview/design philosophy copy in `index.jsx#L7-L48`) is present in the DOM at all times (via `inert` rather than conditional mount), so it is crawlable/indexable even before the user opens the dialog — a mild positive for SEO relative to modals that only mount content on open.
- The demo page correctly implements `generateMetadata` via `getDemoPageMetadata("animated-modal")` ([page.js#L72-L74](<../../../apps/docs/src/app/(marketing)/demo/animated-modal/page.js#L72>)) — checked and clean, not this component's own concern but confirms the preview route is wired for metadata.

## Responsive / mobile / touch behavior assessment

This means responsive behavior is *not* actually identical between "what you preview" and "what you install," which is a meaningful gap for a component whose main job is decorative modal chrome across viewport sizes.

## Security and dependency concerns

- No `dangerouslySetInnerHTML`, no `eval`, no dynamic script injection, no secrets/tokens in source — checked and clean across all three files.
- All rendered content (`popupSections` in `index.jsx`) is static, hardcoded demo copy, not user input — no XSS surface.
- Single external dependency, `lucide-react` for the `X` icon ([AnimatedModalContent.jsx#L5](../../../registry/effects/components/animated-modal/AnimatedModalContent.jsx#L5)), correctly declared in `registry.json#L8-L10`.

## Browser compatibility considerations

- Relies on the `inert` HTML attribute ([AnimatedModalContent.jsx#L91](../../../registry/effects/components/animated-modal/AnimatedModalContent.jsx#L91)) — broadly supported in current evergreen browsers (Chromium 102+, Firefox 112+, Safari 16.4+) but has no fallback for older engines; on a browser without `inert` support, closed-modal content would still be `aria-hidden` (screen readers excluded) but would remain in the tab order, a graceful-ish degradation rather than a hard break. Not flagged as a rubric-level finding since it's a reasonable modern-baseline choice, but worth naming for browser-compat awareness.
- Uses only standard CSS (`backdrop-blur`, arbitrary `vw`/`vh`/percentage values, `z-9999`/`z-99999` bare-number Tailwind v4 utilities) — Tailwind v4 (confirmed in `apps/docs/package.json`) supports bare-number arbitrary values for `z-*` without bracket syntax, so this resolves correctly; the same pattern is used consistently elsewhere in the repo.

## Suggested improvements and remediation priorities

No code was changed as part of this audit, per `CHANGE_GUIDELINES.md`. If addressed later, any fix must not alter visual appearance, responsive breakpoints as experienced by end users, or registry behavior (per `CHANGE_GUIDELINES.md` hard constraints) — in particular, reconciling finding #1 requires an explicit decision on which breakpoint scheme is "correct" (the docs demo's two-tier scheme matches CODING_STANDARDS.md and should probably win), and that decision affects visible layout, so it should be confirmed with the owner before touching either file.

Priority order if this is picked up:
1. Decide and reconcile the breakpoint scheme between the registry and docs copies (#1) — affects real shipped responsiveness, needs owner sign-off per `CHANGE_GUIDELINES.md`.
2. Have the demo (`index.jsx`) pass a real `ariaLabel`/`ariaLabelledby` describing the modal's actual content, and consider adding an `id` to the title in `ScrollablePopupContent.jsx` so any consumer can wire `aria-labelledby` (#2).
3. Add a `prefers-reduced-motion` variant to the opacity transition duration (#3) — low risk, bounded change.
4. Fix `package.json`'s `main`/`files` to point at real files and re-pack a current tarball into `registry/dist/` (#4/#5) — or confirm with the owner that the npm tarball path is deprecated/unused and can be removed instead, since it isn't wired into the CLI install flow.

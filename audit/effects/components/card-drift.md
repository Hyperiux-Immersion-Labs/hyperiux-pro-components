# card-drift (components)

## Summary

`card-drift` is a three-file GSAP `Draggable` component that lays testimonial cards out in a randomized grid and lets users grab, throw, and fling them with velocity-based physics. The core interaction logic (`CardDriftComp.jsx`) is functionally solid — velocity is tracked with an exponential moving average, throw distance/duration scale with drag speed, and cleanup goes through `gsap.context().revert()`. The audit surfaced no crash-level defects, but found a real registry-metadata bug (the npm-pack `package.json` points at a file that doesn't exist, so the packed `.tgz` in `registry/dist/` silently ships without any of the three source files), one shipped-but-never-imported file (`NavigationButtons.jsx`), a Tailwind breakpoint that no longer matches the JS layout math it's meant to pair with, and no accessibility fallback for the drag-only interaction. Registry.json itself (the file that actually drives the CLI install path via `apps/docs/public/r/card-drift.json`) is correct and complete.

## Implementation overview

- `index.jsx` — thin wrapper that hard-codes 5 testimonial objects and renders `CardDriftComp` with a fixed color prop set. [registry/effects/components/card-drift/index.jsx](../../../registry/effects/components/card-drift/index.jsx)
- `CardDriftComp.jsx` — the actual effect. On mount, it measures the container, computes a `cols`/`rows` grid from `sqrt(cards.length)` (collapsing to a fixed 2-column grid under 1025px), scatters each card into its cell with random jitter, then wires each card to `Draggable.create` with `onPress`/`onDrag`/`onRelease` handlers that track velocity via an EMA and throw the card on release, clamped back inside the container bounds. [registry/effects/components/card-drift/CardDriftComp.jsx](../../../registry/effects/components/card-drift/CardDriftComp.jsx)
- `NavigationButtons.jsx` — a standalone prev/next button pair with `aria-label`s and a disabled state, built to page through testimonials. It is not imported by `index.jsx`, `CardDriftComp.jsx`, or anything else in the demo/registry — see Risks below. [registry/effects/components/card-drift/NavigationButtons.jsx](../../../registry/effects/components/card-drift/NavigationButtons.jsx)
- `registry.json` — schema-complete: `name` matches the folder, `type` is `registry:component`, `category` is `components` (valid per [developer-new-component.md#L108](../../../developer-new-component.md#L108)), `main` (`index.jsx`) exists, all three source files are listed in `files` with correct targets, `previewUrl` (`/demo/card-drift`) matches the actual demo route. [registry/effects/components/card-drift/registry.json](../../../registry/effects/components/card-drift/registry.json)
- Demo route renders `<CardDrift/>` with a static instruction pill ("Grab any card and move it around"), sourced from the legacy `apps/docs/src/components/card-drift/` copy, not the registry copy. [apps/docs/src/app/(marketing)/demo/card-drift/page.js](<../../../apps/docs/src/app/(marketing)/demo/card-drift/page.js>)

## Strengths

- Velocity tracking uses an EMA (`alpha = min(1, dt/30)`) rather than a raw single-frame delta, which smooths out jittery throw distances from irregular pointer-event timing. [CardDriftComp.jsx#L108-L124](../../../registry/effects/components/card-drift/CardDriftComp.jsx#L108-L124)
- Throw duration and distance both scale with measured speed and out-of-bounds distance, and the release target is always clamped back inside the container — a card dragged far outside the viewport still animates smoothly back in rather than snapping or getting stuck off-screen. [CardDriftComp.jsx#L134-L164](../../../registry/effects/components/card-drift/CardDriftComp.jsx#L134-L164)
- Layout math distinguishes mobile/tablet/desktop and derives `cellHeight` from actual measured card height on mobile/tablet rather than assuming a fixed size, avoiding layout based on stale/hardcoded dimensions. [CardDriftComp.jsx#L26-L40](../../../registry/effects/components/card-drift/CardDriftComp.jsx#L26-L40)
- All animation setup happens inside `gsap.context()`, and cleanup is a one-line `ctx.revert()` on unmount — the idiomatic GSAP-in-React pattern. [CardDriftComp.jsx#L20](../../../registry/effects/components/card-drift/CardDriftComp.jsx#L20), [CardDriftComp.jsx#L170](../../../registry/effects/components/card-drift/CardDriftComp.jsx#L170)
- `NavigationButtons.jsx`, though unused, is itself accessible in isolation (`aria-label`, `disabled` state wired to an `isAnimating` prop).

## Risks and issues

1. **High — the npm-pack distribution tarball for this component is broken (ships without any source file).** [package.json](../../../registry/effects/components/card-drift/package.json) declares `"main": "card-drift.jsx"` and `"files": ["card-drift.jsx", "registry.json"]`, but no file named `card-drift.jsx` exists in the folder (the real entry is `index.jsx`). Since `build-registry.js` does not regenerate `package.json` when one already exists ([scripts/build-registry.js#L36-L38](../../../scripts/build-registry.js#L36-L38)), it is fed as-is to `npm pack`. I ran `npm pack --dry-run` in the component folder and confirmed the tarball contains only `package.json` (359B) and `registry.json` (932B) — 2 files total, none of `index.jsx`, `CardDriftComp.jsx`, or `NavigationButtons.jsx`. A stale tarball matching this exact broken state already exists at `registry/dist/hyperiux-card-drift-0.0.1.tgz`. **Scoped down from what a broken install path would otherwise be**: I found no reference to `registry/dist/` or `.tgz` files anywhere under `apps/docs/src`, so this does not appear to be wired into the live CLI install flow — that path reads from `apps/docs/public/r/card-drift.json`, which is correct and complete (see below). This is the same pattern already documented for `animated-modal`, `animated-faq`, and `gooey-counter` per a prior audit note in this series (`audit/effects/components/animated-modal.md#L29`), so it is a repo-wide `package.json` authoring bug, not unique to card-drift. Flagged High because *if* this secondary path is ever wired up (or someone hand-installs via the tarball), the component silently fails to install with no source at all — worse than the animated-modal case, which at least ships stale-but-functional code.
2. **Medium — `NavigationButtons.jsx` is dead code shipped on every install.** It is listed in `registry.json`'s `files` array and in the public mirror ([apps/docs/public/r/card-drift.json#L27-L31](../../../apps/docs/public/r/card-drift.json#L27-L31)), and `lucide-react` is a declared dependency solely for its icons, but grepping the whole repo shows it is imported nowhere for this component (registry or legacy copy) — `index.jsx` renders only `CardDriftComp`, which has no prev/next state, no current-index tracking, and no way to invoke `onPrev`/`onNext`. This directly violates the repo's own principle 4, "Dead code is noise — unused variables, attributes, and handlers must be removed before merging" ([CODING_STANDARDS.md#L14](../../../CODING_STANDARDS.md#L14)). Every CLI install of this "free-standing" card grid pulls in an unused component file plus an unused dependency for no functional benefit.
3. **Medium — CSS breakpoint no longer matches the JS layout logic it's meant to pair with.** The JS treats 640–1025px as "tablet" and computes `cellHeight`/`verticalOffset`/column count accordingly ([CardDriftComp.jsx#L27](../../../registry/effects/components/card-drift/CardDriftComp.jsx#L27)), but the rendered card markup only downsizes at the `max-[1025px]:` breakpoint (1280px): `w-96 max-sm:w-42 max-[1025px]:w-60` and `text-9xl max-[1025px]:text-7xl` ([CardDriftComp.jsx#L180](../../../registry/effects/components/card-drift/CardDriftComp.jsx#L180), [CardDriftComp.jsx#L203](../../../registry/effects/components/card-drift/CardDriftComp.jsx#L203), [CardDriftComp.jsx#L213](../../../registry/effects/components/card-drift/CardDriftComp.jsx#L213)). Between roughly 1025px and 1280px the JS believes it is in desktop mode (full `sqrt`-based column count, `containerRect.height / rows` cell sizing) while the card is still forced to the smaller tablet-width CSS class, so the pre-computed cell centering no longer matches the actual rendered card width. The coding standard is explicit that only `max-sm:` (mobile) and `max-md:` (tablet) should be used, consistently, within a component ([CODING_STANDARDS.md#L276](../../../CODING_STANDARDS.md#L276)); this file uses `max-sm:`/`max-[1025px]:` instead. Notably, the legacy docs copy uses `max-md:` at the equivalent lines ([apps/docs/src/components/card-drift/CardDriftComp.jsx#L180](../../../apps/docs/src/components/card-drift/CardDriftComp.jsx#L180)) — meaning the registry copy and the legacy copy have independently drifted to two different, and differently wrong, breakpoints (neither matches the JS's 1025px tablet cutoff, which is closest to Tailwind's default `lg` at 1024px). Bounded to a specific viewport band, not a crash, hence Medium rather than High.
4. **Medium — no accessible/keyboard alternative to drag-only interaction.** The demo's entire content-surfacing mechanism is `Draggable.create(card, { type: "x,y", ... })` on a plain `<div>` ([CardDriftComp.jsx#L85-L166](../../../registry/effects/components/card-drift/CardDriftComp.jsx#L85-L166), [CardDriftComp.jsx#L202](../../../registry/effects/components/card-drift/CardDriftComp.jsx#L202)). Cards are not `<button>`/`role="button"` elements, have no `tabindex`, and there is no keyboard equivalent (arrow keys, Enter, etc.) to move or "throw" a card. The would-be accessible affordance for browsing without a mouse — `NavigationButtons.jsx` — exists but is disconnected (see finding 2). Since the whole point of the component is direct card manipulation, this is a real barrier for keyboard/screen-reader users rather than a cosmetic gap, matching the rubric's High bar ("accessibility failure blocking keyboard/screen-reader users from core functionality"); scored Medium here because the underlying content (the testimonial text) is still present and readable in the DOM/reading order even if it can't be rearranged — the interaction, not the content, is what's inaccessible.
5. **Medium — no `prefers-reduced-motion` handling.** Neither `CardDriftComp.jsx` nor `index.jsx` checks `matchMedia('(prefers-reduced-motion: reduce)')` anywhere (confirmed via repo-wide grep for `reduced-motion`/`prefersReducedMotion`/`matchMedia` in this folder — no matches). The scale-up-on-press and throw-tween-on-release ([CardDriftComp.jsx#L101-L105](../../../registry/effects/components/card-drift/CardDriftComp.jsx#L101-L105), [CardDriftComp.jsx#L159-L164](../../../registry/effects/components/card-drift/CardDriftComp.jsx#L159-L164)) always run at full GSAP-eased duration regardless of user preference. Mitigating factor: this motion is entirely user-initiated (drag/throw), not autoplaying background motion, so the practical impact is bounded — but the rubric lists this exact gap as a Medium example and the repo has no accessibility escape hatch here at all.
6. **Low — inconsistent indentation throughout `CardDriftComp.jsx`.** Every line in the file uses a single leading space regardless of actual nesting depth (e.g. a doubly-nested `cards.forEach` body is indented the same one space as its enclosing `useEffect`) — visible via `cat -e` on [CardDriftComp.jsx#L19-L24](../../../registry/effects/components/card-drift/CardDriftComp.jsx#L19-L24). This isn't a 2-space vs. 4-space style disagreement, indentation has been flattened entirely, which makes the nesting structure (nested nested arrow functions, `Draggable.create` config object, forEach body) hard to visually parse. The identical issue exists in the legacy copy, so it predates the registry/docs split.
7. **Low — legacy docs copy (`apps/docs/src/components/card-drift/`) is a near-duplicate of the registry source, not a re-export.** `apps/docs/src/components/card-drift/CardDriftComp.jsx` is byte-for-byte identical to the registry copy except for the `max-[1025px]:`/`max-md:` breakpoint divergence noted in finding 3. Any future physics/behavior fix applied to one will silently not propagate to the other unless someone remembers both locations exist, per the dual-location workflow described in [developer-new-component.md#L22-L30](../../../developer-new-component.md#L22-L30).

## Accessibility assessment

- `NavigationButtons.jsx` has correct `aria-label="Previous testimonial"` / `aria-label="Next testimonial"` and a `disabled` state — but it is never rendered (finding 2), so it provides zero actual accessibility benefit today.
- No keyboard path exists to reach or manipulate a card (finding 4). No `role`, `tabIndex`, or keydown handler on `.testimonial-card`.
- The decorative background heading (`Draggable Testimonial`) is correctly marked `pointer-events-none select-none` and is purely decorative text, not interactive — no issue there. [CardDriftComp.jsx#L179-L183](../../../registry/effects/components/card-drift/CardDriftComp.jsx#L179-L183)
- Testimonial text itself (`item.text`, `item.year`, `item.tag`) is plain text content, present in normal DOM/reading order regardless of drag position, so screen readers can still read all card content even though they can't reposition cards.
- No `prefers-reduced-motion` gate (finding 5).

## Performance assessment

- No continuous `requestAnimationFrame` loop exists in this component — motion is driven entirely by GSAP's internal ticker during active tweens (press/release/throw) and by GSAP `Draggable`'s own pointer-event-driven update loop, which only runs while a card is actively being dragged. Per the audit brief's rAF-suspension rule, this only needs to be flagged if the effect "genuinely runs a continuous requestAnimationFrame loop" — it does not, so no rAF-suspension (`createSuspendedRaf`) finding applies here, and none was found copied into the folder (correctly absent, not a gap).
- Cleanup is a single `ctx.revert()` covering everything created inside the `gsap.context()` callback. [CardDriftComp.jsx#L170](../../../registry/effects/components/card-drift/CardDriftComp.jsx#L170) I could not independently verify (no test harness available in this audit) whether `Draggable` instances created inside a `gsap.context()` are auto-registered for `revert()`-driven `kill()` by the installed GSAP version — this is the documented GSAP 3.11+ behavior but was not runtime-verified here.
- `Draggable.create` is called once per card inside a single `useEffect` keyed on `[data]` ([CardDriftComp.jsx#L171](../../../registry/effects/components/card-drift/CardDriftComp.jsx#L171)); since `index.jsx` defines `testimonials` as a module-level constant (new array reference only on module reload, not per-render), this effect will not re-run on every parent re-render — no re-creation churn under normal use.
- Layout math (`getBoundingClientRect` calls, grid computation) runs once per mount inside the effect, not per-frame — no per-frame layout thrashing.

## SEO and content-surface assessment

- Testimonial content (`item.text`) is static, server-renderable JSX text — no client-only data fetch blocking content. Content is present in initial HTML/DOM regardless of JS execution, so it is crawlable.
- The component renders a `w-screen h-screen` full-viewport background section with no heading hierarchy beyond a single decorative `<h1>` ("Draggable Testimonial") that is arguably not describing the page's actual primary content (it's a demo caption, not real page structure) — this is standard for an interactive demo page and not a defect specific to this component.
- `generateMetadata` on the demo page pulls from `getDemoPageMetadata("card-drift")`, a shared mechanism not specific to this component — not evaluated here as it's outside the four required files.

## Responsive / mobile / touch behavior assessment

- `w-screen h-screen` on the root container ([CardDriftComp.jsx#L176](../../../registry/effects/components/card-drift/CardDriftComp.jsx#L176)) is a known Tailwind footgun: `100vw` does not subtract scrollbar width, so on any platform where a vertical scrollbar takes up layout space (most desktop browsers without overlay scrollbars), this can introduce a few pixels of horizontal overflow at the document level. Not verified in a live browser as part of this audit (no runtime check performed); flagged as a possible-but-unconfirmed responsive nit, not a scored finding.
- Mobile/tablet cell sizing derives from actual measured card height rather than a hardcoded constant (a strength, see above), but the breakpoint mismatch in finding 3 undermines this for the 1025–1280px band specifically.
- Touch dragging is handled by GSAP `Draggable`, which supports pointer/touch events natively — `type: "x,y"` with no explicit `bounds` config lets a card be dragged fully off the container during the gesture, which is called out in-code as intentional ("No bounds - card can go freely outside during drag", [CardDriftComp.jsx#L87](../../../registry/effects/components/card-drift/CardDriftComp.jsx#L87)) and is then clamped back on release. This is a deliberate design choice, not a bug.
- `cursor-grab`/`active:cursor-grabbing` classes are present for mouse affordance ([CardDriftComp.jsx#L202](../../../registry/effects/components/card-drift/CardDriftComp.jsx#L202)) — appropriate desktop cue, irrelevant on touch (harmless).

## Maintainability and code-quality assessment

- Structure roughly follows the file-structure convention in `CODING_STANDARDS.md` (imports → component → nested `Card` subcomponent), though there's no explicit `──── Constants ────` / `──── Effects ────` section commenting as suggested by [CODING_STANDARDS.md#L18-L35](../../../CODING_STANDARDS.md#L18-L35) — a minor stylistic gap, not scored separately from the indentation finding.
- Naming is clear (`velX`/`velY`, `throwX`/`throwY`, `distOutX`/`distOutY`) and inline comments explain *why* (e.g. "Exponential moving average for smoother velocity", "Extra duration if card is far outside bounds") rather than restating the code, matching the repo's stated commenting principle.
- Two near-identical copies of the same 220-line file exist (registry + legacy docs), already drifted in one place (finding 3, 7) — the DRY principle in [CODING_STANDARDS.md#L15](../../../CODING_STANDARDS.md#L15) is honored within each file but violated across the two copies, which is inherent to the repo's dual-location workflow rather than a component-specific authoring mistake.

## Security and dependency concerns

- No secrets, tokens, API keys, or environment variable leakage found in any of the four files read.
- No unescaped user input rendered as HTML — `item.text`/`item.year`/`item.tag` are all plain JSX text children (React-escaped by default), not `dangerouslySetInnerHTML`. No XSS surface.
- Dependencies declared are `gsap` and `lucide-react` ([registry.json#L8-L11](../../../registry/effects/components/card-drift/registry.json#L8-L11)); `lucide-react` is unused given finding 2 (unused dependency, not a security issue, but unnecessary install weight).
- No unpinned/wildcard version concerns in `registry.json` (it doesn't pin versions at all — consistent with how every other effect in this registry declares dependencies, ecosystem-standard for this repo, not a card-drift-specific issue).

## Browser compatibility considerations

- Relies on `getBoundingClientRect`, `performance.now()`, and pointer events (via GSAP `Draggable`) — all broadly supported in evergreen browsers with no legacy-browser-specific code paths or polyfills needed.
- No use of newer/less-supported CSS or JS APIs beyond standard Tailwind utility classes and GSAP's own cross-browser event abstraction.
- Not tested in an actual browser as part of this audit (no runtime/browser verification was performed — this is a static code review only).

## What was checked and found clean

- `registry.json` schema completeness: `name` matches folder, `type` is `registry:component`, `category` is a valid enum value, `main` (`index.jsx`) exists, all three files are listed with correct `path`/`target` pairs, `previewUrl` matches the real demo route, `tier` is a valid value (`"pro"`). No missing-files-array violation (the specific failure mode called out in [developer-new-component.md#L269](../../../developer-new-component.md#L269)).
- Public mirror (`apps/docs/public/r/card-drift.json`) matches `registry.json` in `name`, `dependencies`, `tier`, `version`, and file list — no drift between source registry metadata and the generated public copy.
- No orphaned imports: every import in all three registry `.jsx` files resolves to either a real relative sibling file or an installed npm package (`gsap`, `gsap/Draggable`, `lucide-react`, `react`).
- `useEffect` cleanup is present and returns a function (`ctx.revert()`) — not missing, unlike some effects in this registry.
- No continuous rAF loop, so the F-042 rAF-suspension pattern (`createSuspendedRaf`/`createVisibilityGate`) genuinely does not apply here — confirmed absent and correctly so, not a gap.
- No XSS/secrets/credential exposure of any kind in any of the four files.
- Data prop (`data = []`) has a sane default and the component won't crash on an empty array (grid math divides by `cols`/`rows` derived from `cards.length`, but `cards` comes from `gsap.utils.toArray(".testimonial-card")` which would also be empty in that case — no cards to lay out, no division-by-zero surfaced in practice since the `.forEach` simply wouldn't execute).

## Suggested improvements and remediation priorities

No code was changed as part of this audit, per `CHANGE_GUIDELINES.md`. If remediation is undertaken later, suggested order (highest-impact first), each to be verified against `CHANGE_GUIDELINES.md` for UI/responsiveness/registry-behavior impact before applying:

1. Fix `package.json`'s `main`/`files` to point at `index.jsx` (and list all three real files), then re-pack `registry/dist/hyperiux-card-drift-0.0.1.tgz` — or confirm with the repo owner that the `npm pack`/`registry/dist` path is fully deprecated in favor of `public/r/*.json` and can be dropped entirely (this appears to be a repo-wide pattern per the animated-modal precedent, so a single fix to `build-registry.js` — e.g. always regenerating `package.json` from `registry.json`'s actual `files` array instead of trusting a hand-authored one — would fix it everywhere at once, consistent with root-cause-over-symptom practice).
2. Either wire `NavigationButtons.jsx` into `CardDriftComp`/`index.jsx` with real prev/next state, or delete it (and the `lucide-react` dependency) from `registry.json`, `package.json`, and the public mirror — currently it's shipped weight with no function.
3. Reconcile the `max-[1025px]:`/`max-md:` breakpoint mismatch with the JS's 640–1025px tablet detection window — likely by switching both to `max-lg:` (1024px, the closest native Tailwind breakpoint to the JS's 1025px cutoff), applied consistently in both the registry and legacy copies.
4. Add a `prefers-reduced-motion` check that at minimum disables/shortens the press-scale and throw-tween durations for users who've opted out of motion.
5. Consider a documented keyboard-accessible fallback (e.g., the disconnected nav buttons, or arrow-key nudging on a focused card) given dragging is the component's sole interaction model.

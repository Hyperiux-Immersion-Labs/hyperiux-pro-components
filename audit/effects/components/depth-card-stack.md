# depth-card-stack (components)

## Summary

`depth-card-stack` is a GSAP-driven 3D card carousel (10 hardcoded demo cards, autoplay, hover-tilt, texture-reveal, chevron navigation) distributed as a 3-file "pro" tier component. The core interaction code is well-structured and cleans up after itself correctly, but the audit found one confirmed release-breaking defect (the npm tarball for this component ships with no source files at all), a real content-drift problem between the registry copy and the newer, bug-fixed copy living in the docs app, a keyboard/screen-reader accessibility gap around the autoplay carousel, and a component that accepts zero props — meaning the "pro" component a customer installs via the CLI ships with Hyperiux's own marketing copy and demo card data hardcoded into the main file.

## Implementation overview

- [`index.jsx`](../../../registry/effects/components/depth-card-stack/index.jsx) — the registry `main` file. Defines a hardcoded array of 10 demo cards (name, member number, color, texture image URL, "claimed X hours ago" text) and renders `DepthCardStackComp` with no props of its own. Exports `DepthCardStack` as default, matching `registry.json`'s `exportName`/`exportKind`.
- [`DepthCardStackComp.jsx`](../../../registry/effects/components/depth-card-stack/DepthCardStackComp.jsx) — the actual carousel: GSAP timelines drive slot-based positioning (`getSlotProps`/`computeSlot`), a 5s `setInterval` autoplay, and a mousemove-driven tilt + radial texture-reveal effect on the centered card.
- [`SliderCard.jsx`](../../../registry/effects/components/depth-card-stack/SliderCard.jsx) — presentational card face (color background, texture overlay with CSS mask, name/joined/member number).
- [`registry.json`](../../../registry/effects/components/depth-card-stack/registry.json) — schema-valid metadata (see below).
- [`package.json`](../../../registry/effects/components/depth-card-stack/package.json) — used for `npm pack`; confirmed broken (see Risks).

## Strengths

- Correct, thorough `useEffect` cleanup throughout `DepthCardStackComp.jsx`: resize listener removed ([`DepthCardStackComp.jsx#L65-L66`](../../../registry/effects/components/depth-card-stack/DepthCardStackComp.jsx#L65-L66)), GSAP timeline killed and rAF cancelled on the layout effect ([`DepthCardStackComp.jsx#L100-L105`](../../../registry/effects/components/depth-card-stack/DepthCardStackComp.jsx#L100-L105)), autoplay `setInterval` cleared ([`DepthCardStackComp.jsx#L202`](../../../registry/effects/components/depth-card-stack/DepthCardStackComp.jsx#L202)), and every hover-tilt listener plus its in-flight enter-ramp rAF is removed/cancelled on unmount ([`DepthCardStackComp.jsx#L309-L317`](../../../registry/effects/components/depth-card-stack/DepthCardStackComp.jsx#L309-L317)).
- All inline event handlers are named functions (`handleEnter`, `handleMove`, `handleLeave`), matching `CODING_STANDARDS.md` §3 "Name all inline functions."
- Both desktop chevron buttons and a duplicated mobile button row are real `<button>` elements with `aria-label="Previous card"` / `aria-label="Next card"` ([`DepthCardStackComp.jsx#L341`](../../../registry/effects/components/depth-card-stack/DepthCardStackComp.jsx#L341), [`#L378`](../../../registry/effects/components/depth-card-stack/DepthCardStackComp.jsx#L378), [`#L390`](../../../registry/effects/components/depth-card-stack/DepthCardStackComp.jsx#L390), [`#L401`](../../../registry/effects/components/depth-card-stack/DepthCardStackComp.jsx#L401)), so both are keyboard-focusable and activatable.
- `registry.json` is schema-complete against `developer-new-component.md`: `name` matches the folder, `type` is `"registry:component"`, `category` is exactly `"components"`, `main` (`index.jsx`) exists, all three source files are listed in `files` with correct `target` paths, and `previewUrl` (`/demo/depth-card-stack`) matches the live demo route.
- The `animating` ref guard prevents overlapping/re-entrant navigation while a GSAP timeline is in flight ([`DepthCardStackComp.jsx#L109-L110`](../../../registry/effects/components/depth-card-stack/DepthCardStackComp.jsx#L109-L110)).

## Risks and issues

1. **[Critical] npm tarball for this component contains no component source — the distribution is empty.** `package.json`'s `main`/`files` point at a file, `depth-card-stack.jsx`, that does not exist anywhere in the folder ([`package.json#L5-L9`](../../../registry/effects/components/depth-card-stack/package.json#L5-L9)); the real files are `index.jsx`, `DepthCardStackComp.jsx`, `SliderCard.jsx`. I verified this is not theoretical: the already-packed tarball at `registry/dist/hyperiux-depth-card-stack-0.0.1.tgz` contains only `package.json` and `registry.json` — confirmed via `tar tzf`, output: `package/package.json`, `package/registry.json`. Anyone installing this component via the npm-tarball distribution channel (`developer-new-component.md` Steps 5/9) gets zero usable code. This is a genuine broken-functionality defect for a shipped artifact, not a hypothetical. Note: this exact `main: "{slug}.jsx"` pattern also appears in sibling `package.json` files (`interactive-list-preview`, `animated-form`, `testimonial-swiper` all reference a single non-`index.jsx` filename that doesn't match their actual multi-file layout), suggesting a repo-wide template bug — but per this audit's scope only the `depth-card-stack` instance is being reported here.

2. **[High] Registry source is stale relative to the (fixed) docs-site copy — a known mobile visual bug and a performance flag were fixed in `apps/docs/src/components/depth-card-stack/` but never copied into `registry/effects/components/depth-card-stack/`.** Diffing the two `DepthCardStackComp.jsx` copies shows the docs-site version has:
   - A `sectionRef` + `forceRepaint` effect with an explanatory comment: *"On mobile, the cards' 3D/composited layers... can leave the section's bottom strip unpainted, exposing the dark body background as a 'black margin'"* — present in `apps/docs/src/components/depth-card-stack/DepthCardStackComp.jsx#L70-L94` but **absent** from the registry copy at [`registry/effects/components/depth-card-stack/DepthCardStackComp.jsx`](../../../registry/effects/components/depth-card-stack/DepthCardStackComp.jsx).
   - `force3D: true` added to every GSAP tween/set call (6 call sites) in the docs-site copy, absent from the registry copy — a GPU-compositing hint that reduces jank for a component making heavy use of `rotateX`/`rotateY`/`scale`.
   - The breakpoint convention was migrated from `max-xl:`/`max-md:` to `max-sm:`/`max-md:`, matching what `CODING_STANDARDS.md` §5 currently documents ("Use `max-sm:` for mobile-specific overrides and `max-md:` for tablet-specific overrides"); the registry copy still uses the old `max-md:`/`max-xl:` pairing throughout (e.g. [`registry/.../DepthCardStackComp.jsx#L321-L353`](../../../registry/effects/components/depth-card-stack/DepthCardStackComp.jsx#L321)).
   - The heading tag changed from `<h3>` (registry copy, [`#L326`](../../../registry/effects/components/depth-card-stack/DepthCardStackComp.jsx#L326)) to `<h1>` (docs-site copy) — the registry copy renders an `<h3>` with no preceding `<h1>`/`<h2>` on the page, a heading-order skip.
   Per `developer-new-component.md`'s intended workflow ("You build in `src/components/`, then copy the source into `registry/effects/`"), the registry — the actual thing customers install — has fallen behind a real bug fix. This is a registry/source-of-truth sync gap with a confirmed, documented visual defect (the black-margin bug) shipping to every installer.

3. **[High] Autoplay only pauses on mouse hover, never on keyboard focus — keyboard and screen-reader users cannot stop the auto-advancing carousel.** `isHoveredRef` is set only by `mouseenter`/`mouseleave` on the card element ([`DepthCardStackComp.jsx#L218-L220`](../../../registry/effects/components/depth-card-stack/DepthCardStackComp.jsx#L218-L220), [`#L275-L277`](../../../registry/effects/components/depth-card-stack/DepthCardStackComp.jsx#L275-L277)); there is no `focus`/`blur` equivalent, and the autoplay `setInterval` in [`DepthCardStackComp.jsx#L196-L203`](../../../registry/effects/components/depth-card-stack/DepthCardStackComp.jsx#L196-L203) has no pause/stop control reachable without a mouse. A keyboard user tabbing to the prev/next buttons, or a screen-reader user reading card content, will have the carousel advance out from under them every 5 seconds with no way to stop it. This fails WCAG 2.2 SC 2.2.2 (Pause, Stop, Hide) for keyboard-only and screen-reader users and fits the rubric's High bucket ("accessibility failure blocking keyboard/screen-reader users from core functionality").

4. **[Medium] The distributed `index.jsx` accepts zero props and hardcodes Hyperiux's own marketing/demo content.** `DepthCardStack` in [`index.jsx#L17-L23`](../../../registry/effects/components/depth-card-stack/index.jsx#L17-L23) takes no arguments; the 10-card array (names like "Hyperiux Core", `claimedText` like "Alexander claimed 2 hours ago", and texture image URLs on Hyperiux's own R2 bucket at `pub-8abee449136941f5b0a1cd2c014534e9.r2.dev`) is baked directly into the file a customer installs. `DepthCardStackComp.jsx` also hardcodes the marketing copy "Hyperiux-UI Library" / "Build futuristic interfaces." / "Crafted for modern web experiences." ([`DepthCardStackComp.jsx#L322-L332`](../../../registry/effects/components/depth-card-stack/DepthCardStackComp.jsx#L322-L332)). This violates `developer-new-component.md`'s own Step 1 code rules ("Accept a `className` prop", "No hardcoded colors - use props with sensible defaults") — neither `className` nor `cards` is exposed as a prop, so every install requires manually rewriting the main file rather than passing data in.

5. **[Medium] Text contrast on light-colored card backgrounds likely fails WCAG AA.** Card `color` values include light hues such as `#93C5FD`, `#FFB33F`, `#C084FC` ([`index.jsx#L7,#L11,#L6`](../../../registry/effects/components/depth-card-stack/index.jsx)), and `SliderCard.jsx` renders label text at `text-white/35` and `text-white/50` on top of that background ([`SliderCard.jsx#L66-L71`](../../../registry/effects/components/depth-card-stack/SliderCard.jsx#L66-L71)). White text at 35–50% opacity over a light pastel background is a low-contrast combination that is unlikely to meet the 4.5:1 (normal text) / 3:1 (large text) thresholds of WCAG 2.1 SC 1.4.3 for at least 3 of the 10 demo cards. Not independently contrast-measured (no automated check was run — flagging as a likely-fail based on the color math, not a guess dressed as fact would require a contrast tool; stated explicitly as unverified by tooling).

6. **[Low] Placeholder-looking literal text "hero" is rendered on every card.** `SliderCard.jsx#L57`: `<p className="text-white text-base">hero</p>` — a static, unlabeled string with no prop wiring, positioned where a category/eyebrow label would normally go. Reads as leftover placeholder content rather than intentional UI copy; not explained by any comment.

7. **[Low] CODING_STANDARDS.md breakpoint-convention deviation.** The registry copy mixes `max-xl:` (tablet) and `max-md:` (mobile) throughout `DepthCardStackComp.jsx` (e.g. [`#L321`](../../../registry/effects/components/depth-card-stack/DepthCardStackComp.jsx#L321), [`#L340`](../../../registry/effects/components/depth-card-stack/DepthCardStackComp.jsx#L340)), whereas `CODING_STANDARDS.md` §5 documents `max-sm:` for mobile and `max-md:` for tablet as the standard to "prefer... consistently instead of mixing multiple mobile/tablet targeting patterns." (Same underlying fact as finding #2's breakpoint diff, listed separately here as a pure style/standards citation.)

8. **[Low] Dead `key` prop on a non-list element.** `SliderCard.jsx#L15` sets `key={card.num}` on the outer `<div>` inside `SliderCard`'s own render — `key` only has meaning on elements produced by a `.map()`/list at the point they're created (already set correctly by the caller in `DepthCardStackComp.jsx#L360`); the one inside `SliderCard.jsx` does nothing and is dead code per `CODING_STANDARDS.md` §"Dead code is noise."

## Accessibility assessment

- Keyboard: prev/next buttons are real `<button>` elements with `aria-label`s and are reachable/operable by keyboard (Strength, above). However, the autoplay pause mechanism is mouse-only (Risk #3, High) — this is the most significant accessibility gap.
- Screen readers: no `aria-live` region announces the active card change; the `claimedText` paragraph updates via a `key`-remount + CSS animation ([`DepthCardStackComp.jsx#L407-L413`](../../../registry/effects/components/depth-card-stack/DepthCardStackComp.jsx#L407-L413)) with no `aria-live="polite"`, so assistive tech gets no notification when the carousel autoplays or is navigated. No `role="region"`/`aria-roledescription="carousel"` or "card X of Y" position indicator is present anywhere in the three files.
- Color contrast: likely-fail on light-background cards (Risk #5, Medium, unverified by tooling).
- `prefers-reduced-motion`: absent. No `matchMedia("(prefers-reduced-motion: reduce)")` check anywhere in the three source files (confirmed via `grep -rn "prefers-reduced-motion\|matchMedia"` — zero matches). Given this component autoplays a spinning/scaling 3D carousel every 5 seconds by default with no way to disable it, this is a real gap, but per the audit's severity rubric it is Medium ("missing best practice with real but bounded impact") rather than High, since it does not block core functionality outright.

## Performance assessment

- No continuous `requestAnimationFrame` loop exists in this component — the only `requestAnimationFrame` usages are (a) a one-shot "ready" frame after mount ([`DepthCardStackComp.jsx#L96-L98`](../../../registry/effects/components/depth-card-stack/DepthCardStackComp.jsx#L96-L98)), which fires once and stops, and (b) a self-terminating ~350ms hover-enter ramp ([`DepthCardStackComp.jsx#L227-L235`](../../../registry/effects/components/depth-card-stack/DepthCardStackComp.jsx#L227-L235)), which stops itself once `enterProgress` reaches 1. Per the audit's scoping instructions, missing `createSuspendedRaf`/`createVisibilityGate` rAF-suspension is only to be flagged when a genuine continuous rAF loop exists — it does not here, so this is **not** flagged as a rAF-suspension finding.
- The `setInterval`-based autoplay ([`DepthCardStackComp.jsx#L196-L203`](../../../registry/effects/components/depth-card-stack/DepthCardStackComp.jsx#L196-L203)) does keep firing every 5s regardless of tab visibility or on-screen status (no `visibilitychange`/`IntersectionObserver` gating) — a `navigate(1)` call and its GSAP timeline will run even if the component has scrolled off-screen or the tab is backgrounded. This is a real but low-magnitude cost (one GSAP timeline over ~10 small DOM nodes every 5s) — logged as Low rather than the Medium rAF-suspension category, since it's a timer, not a continuous rAF loop, and the instructions scope that check specifically to rAF loops.
- Registry copy is missing `force3D: true` on its GSAP tweens/sets, present in the newer docs-site copy (see Risk #2) — a real, if modest, compositing-hint regression for a heavily 3D-transformed carousel.
- No performance profiling/tracing was run as part of this audit; the above is based on static code reading only, not measured frame timings.

## SEO and content-surface assessment

- All headline/body text (`"Hyperiux-UI Library"`, `"Build futuristic interfaces."`, card names, etc.) is static JSX text rendered directly in the component tree, not conditionally injected after mount, so it is present in the server-rendered HTML and crawlable.
- Heading hierarchy: the section renders an `<h3>` ([`DepthCardStackComp.jsx#L326`](../../../registry/effects/components/depth-card-stack/DepthCardStackComp.jsx#L326)) with no `<h1>`/`<h2>` preceding it in this component's own markup (whatever wraps it via `DemoHeader` on the demo page was not audited as part of this component's scope). This is a heading-order skip relevant to both SEO and accessibility; the newer docs-site copy already fixed this to `<h1>` (see Risk #2).
- Texture images are applied via inline `background-image: url(...)` CSS ([`SliderCard.jsx#L42`](../../../registry/effects/components/depth-card-stack/SliderCard.jsx#L42)), not `<img>`/`next/image`, so they carry no `alt` text — acceptable since they are purely decorative overlay textures, not content-bearing images.
- No `next/image`/`next/link` usage question applies here since this component renders no images-as-content or internal links.

## Responsive / mobile / touch behavior assessment

- Three breakpoint tiers are handled: mobile (`≤640px`), tablet (`641–1024px`), desktop (`>1024px`), computed in a resize-listened `check()` function ([`DepthCardStackComp.jsx#L57-L67`](../../../registry/effects/components/depth-card-stack/DepthCardStackComp.jsx#L57-L67)).
- A duplicated, larger touch-friendly button row is shown only on mobile via `max-md:flex` ([`DepthCardStackComp.jsx#L383-L405`](../../../registry/effects/components/depth-card-stack/DepthCardStackComp.jsx#L383-L405)) while the inline desktop chevrons are hidden (`max-md:hidden`) — a reasonable touch-target adaptation.
- Confirmed-missing on the registry copy: the mobile "black margin" repaint fix present in the docs-site copy (Risk #2) — this is a mobile-specific visual regression carried by the registry/distributed version specifically.
- Minor, low-impact layout staleness: the stack container's inline `width` style reads `window.innerWidth` directly only on the `isMobile` branch ([`DepthCardStackComp.jsx#L349-L351`](../../../registry/effects/components/depth-card-stack/DepthCardStackComp.jsx#L349-L351)). Since `isMobile` is derived from a bucketed comparison (`width <= 640`) rather than the raw width, a resize that stays within the same mobile/tablet bucket (e.g. 620px → 600px) does not trigger a re-render and so does not refresh this width value — a stale-until-next-bucket-crossing layout width. Not flagged as a scored finding (cosmetic, narrow window, no crash), but noted for completeness.
- No SSR crash risk from the `window.innerWidth` reference: `isMobile` defaults to `useState(false)`, so during any server render the ternary always takes the `else` branch and never evaluates `window.innerWidth` — verified by reading the ternary short-circuit at [`DepthCardStackComp.jsx#L348-L352`](../../../registry/effects/components/depth-card-stack/DepthCardStackComp.jsx#L348-L352). Listed under "checked and found clean" below.
- Touch/mobile hover-tilt: the 3D tilt and texture-reveal effect is mouse-only (`mouseenter`/`mousemove`/`mouseleave`); there is no touch equivalent, but since it's a purely decorative enhancement and core navigation works via the dedicated mobile button row, this is not a functional gap.

## Maintainability and code-quality assessment

- File organization broadly follows `CODING_STANDARDS.md` §1 (constants at top, component below), and named handlers are used throughout per §3.
- The two-copy-of-truth problem (Risk #2) is the dominant maintainability concern: `apps/docs/src/components/depth-card-stack/` and `registry/effects/components/depth-card-stack/` have diverged with real behavioral/bugfix differences, meaning future edits to one will not automatically propagate to the other, and there's no tooling artifact in this repo enforcing they stay identical.
- `getSlotProps`/`computeSlot` module-level helper functions are a clean, testable extraction of the carousel's slot math ([`DepthCardStackComp.jsx#L14-L39`](../../../registry/effects/components/depth-card-stack/DepthCardStackComp.jsx#L14-L39)).
- Zero-props architecture (Risk #4) means this "component" is really closer to a fixed demo page than a reusable library piece, which will surprise any customer trying to swap in their own card data — they must edit the installed file directly rather than pass props.

## Security and dependency concerns

- No secrets, API keys, or tokens found in source (`grep -niE "api[_-]?key|secret|token|password"` across all `.jsx`/`.json` files in the folder returned only a false-positive match on the demo card name `"Shadow Tokens"`).
- `dependencies` in `registry.json` (`gsap`, `lucide-react`) are legitimate, widely used packages; nothing unusual for a marketplace UI component.
- Texture image URLs are hardcoded to a single external CDN host (`pub-8abee449136941f5b0a1cd2c014534e9.r2.dev`), which the customer's installed project has no control over and which is a single point of failure if that bucket ever moves or is taken down — not a security exposure, but an external hard dependency baked into distributed code, related to Risk #4.
- No `dangerouslySetInnerHTML`, no unescaped user input, no XSS-relevant surface — all rendered text is static/hardcoded, not derived from any external or user-controlled input.

## Browser compatibility considerations

- Uses both `WebkitMaskImage` and `maskImage` for the texture-reveal radial mask ([`SliderCard.jsx#L48-L51`](../../../registry/effects/components/depth-card-stack/SliderCard.jsx#L48-L51)), covering Safari/WebKit alongside standard browsers.
- `mix-blend-mode: screen` (via `mix-blend-screen` Tailwind class, [`SliderCard.jsx#L40`](../../../registry/effects/components/depth-card-stack/SliderCard.jsx#L40)), CSS custom properties (`--reveal-x`/`--reveal-y`), and 3D transforms (`perspective`, `transform-style: preserve-3d`) are all broadly supported in current evergreen browsers; no vendor-prefix gaps were found beyond the mask-image pairing already handled.
- GSAP handles cross-browser transform application, so no manual browser-specific transform code is needed or present.

## What was checked and found clean

- `registry.json` schema completeness against `developer-new-component.md`: `name`, `type`, `category`, `main`, `files` array (all 3 files present with correct `target` paths), `previewUrl`, `tier: "pro"`, `exportName`/`exportKind` all verified correct.
- `main` (`index.jsx`) exists and does export `DepthCardStack` as default, matching `registry.json`.
- Slug/route consistency: registry `name`, folder name, `previewUrl`, and the actual demo route (`apps/docs/src/app/(marketing)/demo/depth-card-stack/page.js`) all agree on `depth-card-stack`.
- `useEffect` cleanup: every `addEventListener`, `setInterval`, `requestAnimationFrame`, and GSAP tween/timeline created by this component has a corresponding teardown path (detailed in Strengths).
- No continuous rAF loop exists, so `createSuspendedRaf`/`createVisibilityGate` non-adoption is correctly *not* flagged as a finding per this audit's scoping rule.
- SSR safety of the `window.innerWidth` reference in the render body — confirmed safe via ternary short-circuit + `false`-default state, not a crash risk.
- No secrets/credentials in source.
- Public mirror (`apps/docs/public/r/depth-card-stack.json`) drift-checked against `registry.json`: no unexpected differences beyond the build script's expected additions (`type` per file entry, `changelog: []`) and expected omissions of build-internal fields (`category`, `main`, `previewUrl`) — consistent with the documented pro-tier "metadata only" public exposure model.
- No automated test suite exists for this component to verify the performance/contrast claims empirically — stated explicitly rather than assumed; both the autoplay-off-screen cost and the contrast-fail claim above are static-analysis judgments, not measured results.

## Suggested improvements and remediation priorities

No code was changed as part of this audit, per instructions. If fixes are made later, `CHANGE_GUIDELINES.md`'s hard constraints apply (no UI/responsiveness/registry-behavior changes without explicit confirmation). Suggested priority order:

1. Fix `package.json`'s `main`/`files` fields to reference the real files (`index.jsx`, `DepthCardStackComp.jsx`, `SliderCard.jsx`) and re-pack the tarball — the current npm distribution is empty (Risk #1, Critical). This is the highest-priority fix since the artifact is already published/packed in `registry/dist/`.
2. Reconcile the registry copy with the docs-site copy — port the mobile black-margin repaint fix, `force3D: true`, and the `max-sm:`/`max-md:` breakpoint convention into `registry/effects/components/depth-card-stack/DepthCardStackComp.jsx`, since that is the version customers actually install (Risk #2, High).
3. Add a `focus`/`blur`-based (or an explicit visible pause control) path to pause autoplay, not just `mouseenter`/`mouseleave`, to fix the keyboard/screen-reader carousel-control gap (Risk #3, High).
4. Consider exposing `cards`/`className` as props with the current hardcoded array as the default, per `developer-new-component.md`'s own Step 1 code rules (Risk #4, Medium).
5. Re-check/adjust text-opacity vs. card-background-color combinations for WCAG AA contrast on the lighter card colors (Risk #5, Medium) — would need an actual contrast-ratio tool run, not just this audit's static read.
6. Low-priority polish: replace the literal `"hero"` placeholder text with real copy or remove it (Risk #6), drop the dead `key` prop inside `SliderCard.jsx` (Risk #8), and align the registry copy's breakpoint prefixes with the documented `max-sm:`/`max-md:` standard (Risk #7 — same underlying diff as #2).

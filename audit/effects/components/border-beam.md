# border-beam (components)

## Summary

Border Beam is a well-engineered decorative wrapper (`BeamBorder`, exported from `BorderBeam.jsx`) that draws an animated rotating or breathing beam of color around any child element using per-instance generated CSS (`@property`-typed custom properties, conic/radial gradients, `mask-composite`) plus a shared, fps-capped `requestAnimationFrame` driver (`PulseDriver.js`) for the two "pulse" size variants. The registry metadata is internally consistent (schema-complete, correct files array, correct `previewUrl`), and the core primitive shows real performance care (single shared 30fps rAF loop instead of 60-120Hz CSS keyframes, `IntersectionObserver`-gated pause when offscreen, proper `useEffect` cleanup). The main gap is that `prefers-reduced-motion` is only honored for the two pulse sizes — the default `md` rotate variant (and `sm`/`line`) keep spinning indefinitely regardless of the OS setting. A handful of Low-severity gaps exist too: an NPM-distribution `package.json`/tarball missing (present for 12/14 sibling `components` effects), a JSDoc/default-value mismatch for `theme`, and small dead config values.

## Implementation overview

- **`BorderBeam.jsx`** — exports `BeamBorder` (forwardRef), the actual reusable primitive. Wraps `children` in a `div[data-beam]`, auto-detects the child's `border-radius` via `useLayoutEffect` + `MutationObserver` (`registry/effects/components/border-beam/BorderBeam.jsx#L98-123`), tracks visibility via `IntersectionObserver` to pause paint-heavy work offscreen (`#L136-150`), measures the child's size for `pulse-outside` glow scaling via `ResizeObserver` (`#L155-191`), and injects per-instance `<style>{cssStyles}</style>` generated by `styles.js` (`#L226-264`).
- **`styles.js`** (2097 lines) — pure functions that build the per-instance CSS string for five size variants (`sm`, `md`, `line`, `pulse-inner`, `pulse-outside`) × 4 color palettes (`colorful`, `mono`, `ocean`, `sunset`), using `@property`-registered custom properties (`--beam-angle-*`, `--beam-opacity-*`, per-oscillator props for pulse) so the values can be smoothly animated/interpolated.
- **`PulseDriver.js`** — a single shared, capped-to-~30fps `requestAnimationFrame` loop (module-level `Set` of registered instances) that ping-pongs CSS custom properties for the two pulse variants only; non-pulse variants animate via plain CSS `animation: ... infinite` and are paused with `animation-play-state: paused` when off-screen (`pausedAnimationsRule`, `styles.js#L851-859`).
- **`index.jsx`** — the CLI/registry "main" entry. It does **not** re-export the bare primitive; it default-exports a fixed demo card (hardcoded English marketing copy, hardcoded hex colors) wrapped in `BeamBorder`. Confirmed this is the repo-wide convention for the `components` category (same pattern in `registry/effects/components/animated-modal/index.jsx`), consistent with a shadcn-style "copy full source, then edit" registry distribution model — not a border-beam-specific defect, but worth knowing before treating `index.jsx` as a generic API.

## Strengths

- Real, measured performance engineering: the pulse breathing used to be ~15 per-instance CSS `@property` keyframe animations running at display refresh rate; it was consolidated into one shared rAF loop capped at ~30fps (`PulseDriver.js#L1-18` doc comment, `#L26` `FRAME_INTERVAL`). This is a concrete, cited optimization, not a generic claim.
- Offscreen animation is genuinely suspended: `IntersectionObserver` (`rootMargin: '256px'`) toggles `isVisible`, which both (a) gates whether `registerPulseInstance` is called at all for pulse sizes (`BorderBeam.jsx#L277-292`) and (b) sets `data-paused` which the CSS pauses via `animation-play-state: paused` for the CSS-driven rotate/line/sm sizes (`styles.js#L851-859`, applied at `BorderBeam.jsx#L334`).
- Correct cleanup everywhere checked: `MutationObserver.disconnect()` (`#L122`), `IntersectionObserver.disconnect()` (`#L149`), `ResizeObserver.disconnect()` (`#L190`), `mediaQuery.removeEventListener` (`#L34`), and `registerPulseInstance` returns an unregister function that also stops the shared rAF loop once idle (`PulseDriver.js#L90-93`).
- SSR-safe: `useIsomorphicLayoutEffect` degrades to `useEffect` on the server (`#L17`), and all `window`/`document`/`matchMedia` accesses are guarded with `typeof window === 'undefined'` checks.
- Registry metadata is internally correct: `name` matches the folder, `type` is `"registry:component"`, `category` is `"components"`, `main` (`index.jsx`) exists, all 4 physical files are listed in `files` with correct `target` paths, and `previewUrl` (`/demo/border-beam`) matches the actual demo route (route group `(marketing)` is invisible in the URL) — verified against `apps/docs/src/app/(marketing)/demo/border-beam/page.js`.
- `className`/`style` props are correctly merged rather than overridden (`#L306-323`), satisfying the "accept a className prop" rule in `developer-new-component.md`.

## Risks and issues

1. **[Medium] `prefers-reduced-motion` is only respected for the two pulse sizes, not the default `md` rotate size (or `sm`/`line`).** The JS-side check at [`registry/effects/components/border-beam/BorderBeam.jsx#L284-289`](../../../registry/effects/components/border-beam/BorderBeam.jsx#L284) only runs inside the pulse-driver effect, which early-returns for non-pulse sizes (`if (!driverConfig) return;`, `#L278`). At the CSS layer, `@media (prefers-reduced-motion: reduce)` blocks exist only inside `generatePulseInnerVariantCSS` ([`styles.js#L1611-1622`](../../../registry/effects/components/border-beam/styles.js#L1611)) and `generatePulseOuterVariantCSS` ([`styles.js#L1797-1808`](../../../registry/effects/components/border-beam/styles.js#L1797)). `generateBorderVariantCSS` (the default `md` size, `styles.js#L1229-1481`), `generateSmallVariantCSS` (`sm`, `#L990-1024`), and `generateLineVariantCSS` (`line`, `#L1812-1850`) contain no such block — I grepped the whole file for `prefers-reduced-motion` and only the two hits above exist. Since `size = 'md'` is the component's own default (`BorderBeam.jsx#L67`) and is what the docs demo page showcases, users with the OS-level reduced-motion preference set still get a perpetually spinning `animation: beam-spin-${id} ${duration}s linear infinite` (`styles.js#L1349-1350` / `#L1120`). Per the audit rubric this is explicitly a Medium ("missing `prefers-reduced-motion` handling").

2. **[Low] `package.json` (and the resulting NPM tarball) is missing for this component, unlike 12 of its 14 `components`-category siblings.** `developer-new-component.md` Step 5 requires `registry/effects/{category}/{slug}/package.json` for `npm pack`/tarball distribution (Step 9), and the Distribution checklist requires the `.tgz` to exist in `registry/dist/`. `ls registry/effects/components/border-beam/` shows only `BorderBeam.jsx`, `PulseDriver.js`, `index.jsx`, `registry.json`, `styles.js` — no `package.json`. `registry/dist/` has 124 tarballs but none matching `border-beam*`. Sibling effects in the same category (`animated-faq`, `animated-form`, `animated-modal`, `animated-tabs`, `card-drift`, `depth-card-stack`, `gooey-counter`, `hover-stack`, `interactive-list-preview`, `ribbon-drift`, `testimonial-swiper`, `video-player`) all have `package.json`; only `border-beam` and `cards-runway` lack one. **Not confirmed** whether this actually blocks the CLI install path today — `border-beam` is `"tier": "pro"`, and per the docs pro-tier code is served via an authenticated API rather than the tarball/public-JSON path, so end-user CLI installs may be unaffected. It is, however, a documented-step gap relative to `developer-new-component.md`, so I score it Low rather than the "breaks the CLI install flow" High bucket, since I cannot verify actual breakage.

3. **[Low] JSDoc/default-value mismatch for `theme`.** The component's JSDoc states `Theme: 'dark' (default) | 'light' | 'auto'` ([`BorderBeam.jsx#L51`](../../../registry/effects/components/border-beam/BorderBeam.jsx#L51)), but the actual default prop value is `theme = 'light'` ([`BorderBeam.jsx#L69`](../../../registry/effects/components/border-beam/BorderBeam.jsx#L69)). A developer reading only the doc comment (or generating docs from it) will get the wrong default.

4. **[Low] Dead config values.** `sizePresets.sm` declares `width: 70` and `height: 36` ([`styles.js#L19-20`](../../../registry/effects/components/border-beam/styles.js#L19)), but neither `BorderBeam.jsx` nor any function in `styles.js` reads `sizeConfig.width`/`sizeConfig.height` (confirmed via grep — zero references). Per `CODING_STANDARDS.md` Core Principle 4 ("Dead code is noise... must be removed"), these two fields are inert and should either be wired up or deleted.

5. **[Low] `index.jsx` (the registry `main`/CLI entry, `exportName: "BorderBeam"`) is a fixed demo card with hardcoded English copy and hardcoded hex colors** (`cardData.title`, `bg-[#f4f5f7]`, `bg-[#ff5a7a]`, `bg-[#45a3ff]`, `bg-[#55d88a]` — [`index.jsx#L3-58`](../../../registry/effects/components/border-beam/index.jsx#L3)), which on its face conflicts with the Step‑1 code rule in `developer-new-component.md` ("No hardcoded colors - use props with sensible defaults"). I verified this is a repo-wide convention for the `components` category (identical pattern in `registry/effects/components/animated-modal/index.jsx`) consistent with a shadcn-style "install full source, then edit" distribution model, and the actually-reusable primitive (`BeamBorder`, accepting `children`/props, in `BorderBeam.jsx`) has no hardcoded colors and is correctly themeable. So this is **not** a border-beam-specific defect — flagging only because it means a CLI installer gets a styled demo card, not a bare wrapper, and must edit `index.jsx` before reuse. No fix suggested; this is a category-wide pattern decision outside this component's scope.

## Accessibility assessment

- The effect is purely decorative (an animated border/glow) and does not intercept focus, keyboard input, or the accessibility tree — `children` pass through untouched inside the wrapper `div`, and the only extra element (`<div data-beam-bloom>`, [`BorderBeam.jsx#L340`](../../../registry/effects/components/border-beam/BorderBeam.jsx#L340)) is empty, non-focusable, and `pointer-events-none`, so it is not announced by screen readers and doesn't need `aria-hidden`.
- `prefers-reduced-motion` is only honored for `pulse-inner`/`pulse-outside` — see Risk 1 (Medium). This is the primary accessibility finding for this component.
- No color-contrast concerns apply to the primitive itself since it wraps arbitrary user content; contrast of that content is the integrator's responsibility.
- No keyboard-trap or missing-label issues found — the component introduces no interactive elements of its own.

## Performance assessment

- Default/`sm`/`line` sizes use native CSS `animation: ... infinite` driven by `@property`-typed custom properties, which the compositor/browser can run off the main thread — no JS per-frame cost for these variants.
- Pulse sizes (`pulse-inner`/`pulse-outside`) are driven by a single shared `requestAnimationFrame` loop capped at ~30fps (`PulseDriver.js#L26` `FRAME_INTERVAL = 1000/30 - 2`) regardless of how many `BeamBorder` instances are on the pulse variants — this scales well with many instances since it's one loop, not one per instance.
- Offscreen instances stop consuming rAF budget: `registerPulseInstance` is only called while `isVisible` (`BorderBeam.jsx#L279`), and the loop self-stops when the registered-instance `Set` is empty (`PulseDriver.js#L71-76`).
- No automated performance test/benchmark exists in this repo for this component (nothing under a `test/` folder for border-beam) — the ~30fps/offscreen-pause claims above are verified by reading the code and its own inline documentation, not by a runtime trace; I did not run one, so this is a static-analysis conclusion, not a measured one.
- `styles.js` generates fairly large per-instance `<style>` blocks (many stacked `radial-gradient`s, especially for the `colorful` variant — up to ~11 gradients per layer). This is static (non-animated) background content; the animated part is only `filter`/`opacity`/CSS custom properties, which is the cheaper thing to animate. No obvious layout-thrashing found.

## SEO and content-surface assessment

- No SEO-relevant markup issues: the component renders no headings, links, or text content of its own (other than the caller-supplied `children`), so it has no effect on document outline or crawlability either way.
- The demo page (`apps/docs/src/app/(marketing)/demo/border-beam/page.js`) supplies its own `generateMetadata` via `getDemoPageMetadata("border-beam")` (`page.js#L89-91`) — not part of the registry component itself, so out of scope for this component-level audit beyond noting it exists.

## Responsive / mobile / touch behavior assessment

- `pulse-outside`'s glow geometry is authored for a fixed reference size (350×140) and rescaled per-axis to the actual wrapped element via `ResizeObserver`, clamped to `[0.35, 4]× ` (`BorderBeam.jsx#L152-191`) — this is a deliberate, well-considered responsive mechanism for a size-sensitive visual effect.
- Border radius auto-detection re-runs on child mutation (`MutationObserver`, `childList`/no `subtree`), so radius changes from responsive class swaps on the *direct* child are picked up; radius changes from a deeper-nested element wouone't be caught, but that's a reasonable, intentionally-scoped limitation (not something a `subtree: true` fix could cheaply generalize without perf cost) — no fix suggested.
- No touch-specific interaction exists (the component isn't interactive), so there's nothing to fail on touch devices; `onActivate`/`onDeactivate`/`active` prop toggling works identically regardless of input modality.
- The demo page itself (`page.js`) uses `max-md`/`max-sm` responsive Tailwind classes throughout — reasonable, standard responsive layout, not part of the distributable component.

## Maintainability and code-quality assessment

- `styles.js` is large (2097 lines, ~88KB) with substantial repetition across `colorPalettes`, `smallColorPalettes`, `lineColorPalettes`, `lineInnerGradientData`, and `lineBloomColors` — five separate near-parallel per-variant/per-color-scheme data tables. This is a genuine `CODING_STANDARDS.md` Rule 5 ("extract any logic that appears more than twice") tension, though the values differ enough (different pixel sizes/positions per size class) that a naive extraction could easily reduce readability rather than improve it — flagging as an observation, not a scored finding, since no obvious safe consolidation is apparent without visual regression risk.
- Naming is otherwise clear and consistent (`isActive`/`isFading`/`isVisible`, `detectedRadius`, `pulseGlowScale`), and comments explain *why* (e.g. the rAF-consolidation rationale in `PulseDriver.js#L1-18`, the `MutationObserver` layout-glitch rationale in `BorderBeam.jsx#L98-101`), matching `CODING_STANDARDS.md` Principle 3.
- `themeColors` in `styles.js#L143-146` is explicitly marked `@deprecated`, kept only for backward compatibility, and is not otherwise referenced in `BorderBeam.jsx` — correctly labeled dead-but-intentional, not flagged as an issue.
- See Risk 4 for the two genuinely dead (`sizePresets.sm.width`/`.height`) values.

## Security and dependency concerns

- `dependencies: []` in `registry.json` is accurate — the component imports only React (`forwardRef`, `useId`, `useEffect`, `useLayoutEffect`, `useState`, `useCallback`, `useMemo`, `useRef`) and its own local files; no third-party runtime dependency.
- No secrets, tokens, API keys, or credentials found in any of the 4 source files (grepped for `console.`/`debugger` too — none found).
- No use of `dangerouslySetInnerHTML`, `eval`, or any user-string-to-DOM injection. The injected `<style>{cssStyles}</style>` (`BorderBeam.jsx#L327`) is built entirely from component props (numbers, enum-like strings, a generated `id`) interpolated into a template literal, not from arbitrary/unescaped end-user text, so there is no realistic CSS-injection/XSS vector here.

## Browser compatibility considerations

- The rotate/line/sm animation mechanism depends on the CSS Properties and Values API (`@property`, used to type `--beam-angle-${id}` as `<angle>` so it interpolates smoothly across the `beam-spin` keyframes at [`styles.js#L1212-1214`](../../../registry/effects/components/border-beam/styles.js#L1212) and registered at `#L1329-1339`). This is Baseline-available in current evergreen browsers, but there is no `@supports`/fallback path — on a browser without `@property` support the custom property would not animate, and the beam would likely render static rather than rotating (degraded, not broken/crashing).
- `mask-composite` is correctly dual-authored for both engines: `-webkit-mask-composite: xor` alongside standard `mask-composite: exclude` (e.g. `styles.js#L1589-1592`), which is the correct historical mapping between the two specs — good cross-browser handling, not a gap.
- `ResizeObserver`/`IntersectionObserver`/`MutationObserver` are all broadly supported in evergreen browsers and are feature-detected/guarded (`typeof ... === 'undefined'` checks at `BorderBeam.jsx#L138`, `#L183`) before use, so older or non-standard environments degrade gracefully (feature simply doesn't activate) rather than throwing.
